# Панель производства и безопасного управления

Запускать итоговую сборку `integration/production-safety`. Один процесс Runner владеет транспортом
Купола и Gate. Панель, алгоритмы, модель и сервисные команды используют этот путь; нового соединения
с ключом команды, serial/SSH/Klipper/GRBL, отдельного диспетчера файлов и специального восстановления
ЧПУ здесь нет. RAG, исходные журналы, рабочие данные и модель выбранной базы сохранены.

## Запуск

```bash
python -m pip install -r integration/requirements.txt
python run_panel.py
```

Панель: `http://127.0.0.1:8080/ui/`. База создаётся пустой. Старт не подключает живой Купол,
не вызывает модель и не запускает производство. Подключение — обычной кнопкой панели.
При заданном `DATA_API_TOKEN` введите токен слева; все REST-маршруты наследуют авторизацию,
защиту Origin и HTTP-аудит. Ключи и `.env` не коммитить.

| Настройка сервера | Значение |
|---|---|
| `DOME_API_SCOPE` | `history` по умолчанию; `full` включает разрешённый живой API |
| `DEPLOYMENT_PROFILE` | `competition` по умолчанию; `service` только вне соревновательной смены |
| `AGENT_MODE` | `recommendation` по умолчанию; также `off`, `autonomous` |
| `ALGORITHMS_ENABLED` | `1` по умолчанию; независим от режима модели |
| `DOME_URL`, `DOME_KEY` | Адрес и ключ организаторов, используются только при подключении |
| `DOME_ALLOW_CONTROL` | Только `1` допускает реальную отправку; `AGENT_DRY_RUN=1` приоритетнее |
| `DEEPSEEK_API_KEY`, `DEEPSEEK_BASE_URL` | Только согласованный организаторами DeepSeek |
| `DEEPSEEK_MODEL` / `LLM_MODEL` | Существующий выбор модели сохранён; сверить со списком организаторов |
| `PRINTER_SUPERVISION_S` | Период надзора 10–15 с, по умолчанию 12 |
| `PRODUCTION_APPROVED_SHA256` | Через запятую SHA-256 файлов G-code, подготовленных организаторами; пусто запрещает upload |
| `CRITICAL_LINE_MAP` | JSON-словарь подтверждённых дополнительных критических нагрузок: node_id → линия |
| `YELLOW_NOZZLE_SAFE_C` | Порог переходного охлаждения сопла, по умолчанию 50 °C; стол — `checks.printer.cool_bed_c` |
| `YELLOW_PLAN_TIMEOUT_S` | Общий предел однократного жёлтого плана, по умолчанию 180 с |
| `PANEL_STATE_DIR` | Необязательный каталог состояния; иначе отдельный по серверу/ключу/БД |
| `PANEL_PORT`, `DATA_API_DB`, `DATA_API_TOKEN` | Порт, путь существующей SQLite и её HTTP-токен |

`history` означает просмотр/анализ уже имеющихся записей. Он не подключает управляющий WebSocket,
не доказывает текущую безопасность и не даёт start/resume/upload/line_on или сообщения в meeting_01.
Объём доступа оставлен настройкой, поскольку уточнение владельца о «только API логов» не получено.
Исторические данные в эту сборку автоматически не импортируются.

## Вкладки и обновление

Панель опрашивает сервер каждые 4 с. Раскрытые блоки (`<details>`), прокрутка внутри блоков, введённые значения и фокус
сохраняются при любой перерисовке на всех вкладках (`web/ui-state.js` перехватывает запись `innerHTML`; запись, не
меняющая разметку, пропускается).

- **Обзор:** метрики, узлы одной сеткой, пять последних событий и переход ко всем.
- **Узлы:** все узлы по группам каталога (энергия, климат, производство, безопасность и т. д.), у каждого состояние из
  последней телеметрии, возраст данных, все поля и раскрывающийся блок «Воздействия». Воздействия берутся из
  `controls` каталога `describe_nodes`, как на вкладке «Управление»: операторские действия только перечислены, отправка
  только в сервисном профиле для текущего запуска и после подтверждения; команда идёт тем же `POST /control/commands` и
  всем проверкам Gate. Для значений есть подсказки по справочнику узлов (списки, числа с диапазоном, файлы из
  телеметрии, JSON). Поиск по узлу и фильтры «только с проблемами» и «только с воздействиями».
- **События:** лента, как была на главной: решения агента, воздействия, сообщения Оператору, с фильтром по виду, числом
  записей и поиском по тексту.

Проверка в браузере: `tests/test_browser_panel.py` (Chrome, Chromium или Edge; иначе пропускается).

## Режимы и маршрутизация

- Рекомендательный: модель предлагает, её воздействия не исполняются, совет уходит Оператору в чат, решение
  записывается в журнал без команд (при `DOME_API_SCOPE=history` — с пометкой `proposed_only`). Алгоритмы работают как обычно. Принятие рекомендации — сервисная ручная команда через Gate.
- Автономный: плейбуки и модель работают **параллельно**. Плейбук действует первым по своим узлам; модель получает
  все поводы, в том числе по узлам, которые ведёт плейбук, и раздел «Алгоритмы» (что они сделали и чего ждут).
  Шаг модели по узлу, которым занят плейбук (команда в ожидании проверки или моложе `policy.algorithm_hold_s`, 30 с),
  не исполняется: он остаётся в плане решения и в ответе Оператору как «отложено». Остальные узлы и случаи, где
  плейбуков нет, модель исполняет сама. При критическом или физическом вмешательстве — структурированный вызов человека.
- «Только ИИ-агент»: прекращаются новые вызовы модели, старые результаты обесцениваются, алгоритмы работают.
- «ИИ-агент и алгоритмы»: обе подсистемы выключены; телеметрия, журнал, тревоги и сервисные команды доступны.

Модель делает по решению один проверяемый шаг. Когда Gate подтверждает его по свежему кадру, модель получает повод
«Проверка результата» и решает про следующий шаг заново, по новой телеметрии (отложенные шаги в нём перечислены).
Вопросы Оператора о состоянии и свободные вопросы отдаются модели, пока она здорова; плейбук Заданий отвечает только на
команды (файл, подтверждение, «забрала», разблокировка). Без модели эти вопросы отвечает плейбук, как раньше.

Режим авторитетен на сервере для всех вкладок; `policy_epoch` меняется при переключении и потере
сессии. Gate проверяет политику и состояние снова перед записью в сокет, после общего ограничителя.
`confirmed=true` не обходит ни одну проверку. Прямое ручное управление в competition запрещено,
включая старый путь через БД. Задачи передаются агенту; физические действия — Оператору.
Аппаратная защита Купола остаётся действующей при любом выключении наших алгоритмов.

Исключение плейбука, локальный отказ Gate на предложение алгоритма (кроме «ожидает проверки»), отказ или таймаут
команды Купола и неподтверждённый эффект создают явный повод для модели. Свою ошибку модель тоже разбирает сама,
но не по кругу: больше трёх сбоев её команд за 10 минут (`AGENT_FAILURES_BEFORE_HUMAN`) уходят человеку. Если ИИ
выключен или недоступен, не предложил нового шага после отправленной, но не подтверждённой команды либо запросил
человека (`request_human`), создаётся инцидент. Локальный отказ Gate, который Купола не касался, сам инцидента не
создаёт. Ошибка доставки в чат не создаёт цикл вызовов модели. Сообщения, обработанные правилами, исключаются
из разбора модели по конкретным id.

Данные для разметки воздействий и правила свежей телеметрии (Gate, диспетчер, `no_data`) работают поверх этой схемы
без изменений: проверка эффекта принадлежит Gate, а подтверждение без нового кадра узла не засчитывается.

## Производство

Раздел содержит принтер `printer_3d_01` и ЧПУ `cnc_01`: свежесть, состояние, файл, удержание/ошибка,
последнее воздействие, progress/elapsed/ETA. Рабочие и машинные координаты ЧПУ подписаны отдельно.
ETA берётся из телеметрии; резервная оценка появляется только по нескольким устойчивым новым точкам.
При неизвестном значении показано «нет данных». Webhook COMPLETED не доказывает завершение.

Файлы запрашиваются штатным `list_files`; один файл выбирается и запускается отдельным `start_job`.
Resume идёт через тот же Gate с проверкой задания, координат, интерлоков и фактического продолжения.
Каждая операция имеет UUID: повтор HTTP/клика не создаёт второй start. После неизвестного исхода —
сверка, без автоматического повтора. Exactly-once для стороннего оборудования не обещается.

Upload доступен только принтеру, при наличии действия в свежем каталоге и разрешённого хеша файла.
UTF-8, до 16 МБ, готовый G-code, безопасное имя, без перезаписи выполняемого файла. Локальный SHA-256
сохраняется как идентичность содержимого; API не всегда возвращает контрольную сумму записанного
файла, поэтому побайтовая удалённая идентичность без неё не объявляется проверенной.

Пауза/отмена станков запрещены API §7.1; upload ЧПУ отсутствует. Кнопки явно недоступны и не заменяются
отключением питания. Очереди файлов, автоматического следующего старта, разбиения УП, потоковой
отправки, CAM/слайсинга и восстановления ЧПУ по координатам нет. TasksPlaybook принимает один файл
для немедленного старта; при занятости/неготовности запрос отклоняется без сохранения на будущее.
После устранения причины нужна новая команда с именем файла. Старые queued/waiting_confirm
записи удаляются, начатые задания только наблюдаются. Исторический чат при старте не исполняется.
См. [маршрут и сравнение веток](../docs/Dome_changes_and_routing_27-10-2026.md).

Надзор принтера работает на сервере без открытого UI. Автовосстановление — один resume того же
сохранённого задания, только после новой проверки устранённого программного IL_CO2/IL_CONDENSATE.
Ручная/неизвестная пауза, FILAMENT_RUNOUT, BED_COLLISION, дым, потеря питания/координат, IDLE/ABORTED
не восстанавливаются автоматически. Явная новая команда Оператора агенту — отдельное намерение,
которое всё равно проходит Gate; квитирование тревоги таким намерением не является.
Порог stall по умолчанию не установлен: при необходимости задаётся `checks.printer.stall_timeout_s`
в `agent/dome.yaml`; нагрев/хоуминг не считаются зависанием по одному неизменившемуся проценту.
В текущем API нет запроса полного обновления телеметрии: при устаревании ожидается push, действие блокируется.

## Уведомления и кнопки

Инциденты сохраняются в существующем журнале/БД, восстанавливаются после перезапуска, объединяются
по эпизоду. Повышение yellow → red доставляется отдельно. «Принял» меняет только ack, не устраняет
риск и не вызывает API acknowledge интерлока. Старые события отмечены историческими до новых данных.
Каналы — панель и meeting_01; dry-run/ошибка доставки не объявляются успешным вызовом оператора.

Жёлтая сразу выключает ИИ и обычные алгоритмы, отменяет их планы и вызывает Оператора. В service/full
затем выполняется один ограниченный план отключения второстепенных линий 1,2,3,4,5,6,8. Линия 7,
критические нагрузки и переходные охлаждение/вытяжка сохраняются. Линия 1 смешанная: при неизвестном
окончании продувки она остаётся включённой, пайку просят выключить физически. Химлаб также сохраняется,
пока безопасное окончание продувки не подтверждено. В API отсутствует гарантированный признак purge_required:
его отсутствие трактуется как неизвестность, поэтому жёлтый план может закончиться частичным результатом.
Статусы requested/accepted/verified/ambiguous/failed разделены. Нельзя объявить всё выключенным по ACK.

Дополнительного latch/reset после жёлтой нет. Обычные переключатели снова включают режимы,
ручной line_on отменяет конфликтующий неотправленный шаг, смена режима отменяет остаток плана.
Питание автоматически обратно не включается. В competition ручной план питания не исполняется.

Красная — **полный выход нашего приложения**, без подтверждения. Сразу закрывается допуск новых
действий, отменяются отложенные результаты и останавливается браузерный опрос. Через ограниченный
flush (предел 0,75 с) завершается HTTP/Runner/WS/потоки, launcher завершает принадлежащее приложению
дерево процессов и сам выходит. Сервер Купола и чужие процессы не завершаются. Кнопка не обесточивает
оборудование. После этого обычный `python run_panel.py` запускает приложение без reset и проверки
«нормализации». Автоподключение/автовоспроизведение старых команд не добавлены.

Для полного killswitch использовать именно launcher; прямой uvicorn не владеет деревом процессов
и честно отклоняет красную с объяснением. Пример systemd — `dome-panel.service.example`;
намеренный красный выход launcher возвращает 0. Не ставить внешний `Restart=always`/container restart=always.
Windows-путь управления дочерними процессами реализован через psutil; фактическая процессная проверка
выполнена на Linux, на Windows её ещё нужно повторить.

## Графики (27.10.2026)

На странице графиков сразу показаны 20 основных рядов: генерация, нагрузка, заряд,
напряжение/ток/температура АКБ, выход/температура инвертора, сеть, генератор, три CO₂,
температура и влажность воздуха, щиток, прогресс печати/фрезеровки, сопло и вода.
Аномальные ряды (включая неизвестные поля вне этого набора) автоматически поднимаются
наверх и выделяются ярко-жёлтым с объяснением. Обновление — раз в 4 секунды при открытой
вкладке браузера. Значения вне рабочего диапазона, статистические отклонения и пропуски
требуют проверки; жёлтый цвет сам по себе не означает доказанную аварию.

Карточки узлов обновляются на месте: раскрытие полей и прокрутка JSON сохраняются.
Потоки различных запусков, источников и WS-сессий имеют отдельные истории анализа.
Численные пределы предупреждений перечислены в `agent/src/kupol/dome/monitoring.py`; это рабочие
эвристики, а не пороги аппаратной защиты. Для фонового статистического сравнения
нужно минимум 12 различных отсчётов; пороги и пропуски проверяются сразу.

Плановый обзор LLM — раз в 180 секунд по умолчанию (меняется в панели или через
TRIGGER_REVIEW_S); любой другой вызов модели сдвигает таймер. Числовые предупреждения идут
поводом `numeric` с низким приоритетом. Без свежих данных результаты команд не считаются
подтверждёнными — это проверяет код (Gate, диспетчер, итог требования Оператора).

Разделение воздействий (базовое, скрытое, каскадное, ложный сигнал) делает LLM-агент; страница
графиков показывает его последнюю оценку и замечания проверки. Эпизоды логов недели размечены
в RAG Купола (ситуации S25–S53) и попадают в промпт обычным поиском RAG. Форматы: [контракт наблюдения](../contracts/telemetry-monitoring.md).
Результат: **61 + 14 Python-проверок**; отдельный DOM smoke `tests/web_ui_smoke.cjs` с jsdom.
Пример: `npm install --prefix /tmp/dome-ui-test jsdom`, затем
`NODE_PATH=/tmp/dome-ui-test/node_modules node tests/web_ui_smoke.cjs`.

Все БД и run_id тестовые, без архивного импорта, платной модели или реального оборудования. Процессный
smoke использует отдельный эмулятор, зависшие дочерний процесс и поток: после красной порт закрыт,
дерево приложения завершено, эмулятор жив, обычный повторный запуск успешен. Проверены также
профили/auth, два клиента, поздний ответ модели, fresh/stale Gate, resume, дедупликация/ack, ETA,
повтор операции и частичный жёлтый план с линией ЧПУ.

Расширенный старый набор `agent/tests/test_dome_llm_brain.py` и `test_dome_resilience.py`:
45 прошли, 8 не прошли. В отдельной копии версии до этих исправлений воспроизведены те же
8 неуспешных сценариев; они не объявляются закрытыми этим изменением. Старые harness используют
стартовую политику history/recommendation, а часть ожиданий относится к прежнему маршруту ИИ.

Визуальная браузерная проверка мобильной вёрстки заблокирована средой: Cloud Browser отвергает localhost
(ERR_BLOCKED_BY_CLIENT), CDN Chromium возвращает Site Unavailable вместо архива. DOM-поведение и
синтаксис JS проверены; проверка реального layout/hover/touch на телефоне остаётся открытой.

## Чтение датчиков внутри запроса

LLM может вызвать `read_sensor(node_id, fields)` до окончательного ответа: например,
`{"node_id":"climate_sensor_01","fields":["co2_ppm","humidity_pct"]}`. Инструмент
читает выбранные скалярные поля из последнего снимка в момент вызова. Он доступен
как автономному агенту, так и разовому анализу из панели; включать управление для
него не требуется. Через этот инструмент команды оборудованию не отправляются.

Жёсткий лимит — три обращения на весь запрос, вместе с повторными раундами модели
и ошибками. Четвёртое блокируется кодом. Ответ содержит исходные метки и fresh;
старый снимок или неизвестная свежесть явно обозначаются. Это чтение телеметрии,
а не принудительный физический опрос: универсального запроса датчика в API Купола нет.
Попытки и их результаты сохраняются через EventSink как sensor_read и связаны с
решением через sensor_read_event_ids. При отключённом EventSink записи в БД нет.
Подробности: [контракт чтения](../contracts/sensor-reads.md).
