# Новая веб-панель + текущий llm layer + БД/API

> **Адаптация под агент с LLM-основой.** Своего соединения с Куполом и своего Gate у панели больше нет.
> Кнопка «Подключить Купол» запускает агент из `agent/` (`Runner`: LLM-основа, плейбуки — запасной путь,
> Gate, проверка эффекта, запись в эту же БД). Решения агент принимает сам, а флажок на странице «LLM-агент»
> включает и выключает LLM-основу. Команда человека и сообщение в чат — это намерение `source=operator`
> ([contracts/manual-control.md](../contracts/manual-control.md)): его проверяет сервер, исполняет агент через Gate,
> итог записывается событием `control_dispatch`. Новая страница «Чат с Оператором» — переписка `meeting_01`
> и отправка сообщений.
>
> **Тестовый режим на эмуляторе Купола**, без реального оборудования:
>
> ```bash
> python -m integration.demo_dome          # эмулятор: ws://127.0.0.1:8765, ключ DEMO-KEY-123456
> DATA_API_DB=state/demo/data-api.sqlite3 DOME_URL=ws://127.0.0.1:8765 DOME_KEY=DEMO-KEY-123456 >   DOME_ALLOW_CONTROL=1 KEYS_FILE=Keys/team_1.txt python run_panel.py
> ```
>
> Откройте http://127.0.0.1:8080/ui/ и нажмите «Подключить Купол». Без ключа DeepSeek решения принимают плейбуки.

## Быстрый запуск

Из корня этой ветки, Python 3.11+:

```bash
python -m venv .venv
# Windows:
.venv\Scripts\python.exe -m pip install -r integration/requirements.txt
.venv\Scripts\python.exe run_panel.py
# Linux/macOS:
# .venv/bin/python -m pip install -r integration/requirements.txt
# .venv/bin/python run_panel.py
```

Открыть **http://127.0.0.1:8080/ui/**. Один процесс/worker, один HTTP origin для панели,
БД/API, управляющих маршрутов и аудита. Старт создаёт **пустую** SQLite
`state/data-api.sqlite3`. История, симуляции и samples не импортируются.
Первоначально нет ни WebSocket-соединения, ни вызовов LLM, ни отправки команд.
При другом порте задать `PANEL_PORT`; launcher согласует с ним DATA_API_URL.
При ручном запуске uvicorn согласуйте DATA_API_URL самостоятельно.

Переменные задаются в окружении или корневом `.env` (не коммитить):

| Переменная | Назначение |
|---|---|
| DATA_API_DB | Путь SQLite; по умолчанию state/data-api.sqlite3 |
| DATA_API_TOKEN | Токен всех HTTP API; в панели ввести слева, передаётся заголовком Authorization |
| DATA_API_RUN_ID | Необязательный ID запуска, иначе создаётся новый web-UUID при старте |
| DATA_API_URL | Внутренний адрес сервиса для текущего llm_agent; launcher задаёт loopback |
| DOME_URL / DOME_KEY | URL и ключ Купола; используются только после кнопки подключения |
| DOME_ALLOW_CONTROL | Только значение 1 разрешает живую отправку через Gate |
| AGENT_DRY_RUN | Значение 1 приоритетно запрещает реальную отправку |
| DEEPSEEK_API_KEY | Ключ текущего LLM-слоя, хранится только на сервере |
| LLM_MODEL / DEEPSEEK_BASE_URL | Модель и endpoint из текущего llm_agent/config.py |
| PANEL_PORT | Порт launcher, по умолчанию 8080 |

Ключи также поддерживаются существующими loaders через KEYS_FILE. Настройки моделей
и правила agent/dome.yaml не подменяются интеграцией. RAG в этом запуске выключен;
промпты, структурированный выход и проверки берутся из текущего llm_agent.
Токен панели хранится только в sessionStorage текущей вкладки, не в URL.
При DATA_API_TOKEN защищены все API, сама статическая страница входа общедоступна.

## Что работает

- **Обзор:** выбранный запуск, полные снимки всех узлов, online/status, события.
- **Графики:** выбор узла и числового поля, несколько графиков, последние 240 снимков;
  null и отсутствующие значения дают разрывы. Время получения и исходные метки различаются.
- **Управление:** человек выбирает действие из полученного каталога и JSON-значение,
  подтверждает команду. Сначала сохраняется control_intent, затем проверка БД и Gate.
  Нет контекста/соединения — сохраняется отказ, команда не отправляется.
- **Журнал воздействий:** автор agent/operator, локальный допуск, результат Gate,
  отдельный accepted/rejected/pending/ambiguous ответа Купола. Dry-run явно помечен
  как «не отправлено». Принятие не объявляется доказательством физического выполнения.
- **LLM:** просмотр фактического промпта из БД, вызов текущего DomeLLMAgent, полный
  структурированный ответ, llm_request/llm_response/decision в БД. Промпт можно посмотреть
  без ключа модели. Ошибка модели не превращается в управляющую команду.
- **Предложения агента:** каждое действие исполняется отдельной кнопкой после новой
  проверки БД и Gate; periodic analysis создаёт только решения, команды автоматически
  не исполняет. Одно действие одного решения имеет устойчивый серверный ID, повтор
  HTTP/перезагрузка не отправляют его повторно. Для повторной попытки нужно новое решение.
- **База:** фильтры, пагинация, просмотр полного JSON, поиск event_id, экспорт текущей
  страницы JSON и просмотр полных HTTP-запросов/ответов без секретов. Произвольного SQL
  и прямой записи в таблицы из браузера нет.

Панель управления работает с текущим runtime.run_id. Выбор исторического запуска
предназначен только для просмотра. Физические operator_controls не отправляются через
Gate: это действия человека на оборудовании; их можно попросить через meeting_01.
Политика Gate применяется также к командам человека, без обхода блокировок.

## Соединение компонентов

`integration/server.py` собирает существующий data_api и маршруты `/control/*`.
`integration/runtime.py` владеет одним DomeClient и существующим Gate; алгоритмы решений
не переписываются. Кадры WebSocket синхронно фиксируются тем же Store, что обслуживает
HTTP API; auth-ключи и известные секреты удаляются до записи. Ошибка фиксации кадра
не замалчивается интеграционным клиентом. Новый session_id назначает сам DomeClient.

Текущий llm_agent читает и пишет **через существующий HTTP API**, используя активный run_id
и session_id. Модель не получает доступ к отправке WebSocket-команд. Запросы панели и
все новые API-маршруты проходят полный аудит, включая отказы Origin/auth/валидации.
Сторонний browser Origin для изменяющих запросов отклоняется.

Минимальное расширение транспорта `agent/src/kupol/dome/client.py`: необязательный
request_id у request/control. Оно сохраняет ID предварительно проверенной команды
при реальной отправке и защищает от коллизии одновременно ожидающих ID. Клиент остаётся
единственным транспортом; его обычные вызовы без request_id работают как прежде.

Намерение и исходящий control — разные события; связи в metadata.intent_event_id и
metadata.decision_event_id. Автор исходящего control сохраняется operator/agent.
Весь ответ Купола сохраняется целиком. После таймаута нет автоматического повтора:
результат неизвестен, проверять ответ/состояние отдельно. Если процесс оборвался после
начала отправки, повтор операции с тем же ID не отправит команду снова.

Проверка физического эффекта не выводится из текста модели: для неё нужны формализованные
Expect существующего Gate и новые измерения. При отсутствии такой проверки UI явно
оставляет эффект неподтверждённым; здесь он не объявляется выполненным автоматически.

## Минимальные проверки

```bash
python -m pytest integration/test_smoke.py -q
node --check integration/web/app.js
```

Три offline smoke-проверки: пустой старт/auth/HTTP-аудит; сохранение отказа человека и
защита от повторной отправки; реальный сборщик промпта и текущий LLM-слой с тестовым
ответом, записывающие запрос/ответ/решение через API. Все SQLite временные, без импорта
данных. К Куполу и внешней LLM при разработке не подключались. Графический браузер
в окружении проверки отсутствовал: проверены выдача HTML/JS и синтаксис JS, визуальная
проверка панели в браузере не выполнялась.

## Графики (27.10.2026)

На странице графиков сразу показаны 20 основных рядов: генерация, нагрузка, заряд,
напряжение/ток/температура АКБ, выход/температура инвертора, сеть, генератор, три CO₂,
температура и влажность воздуха, щиток, прогресс печати/фрезеровки, сопло и вода.
Аномальные ряды (включая неизвестные поля вне этого набора) автоматически поднимаются
наверх и выделяются ярко-жёлтым с объяснением. Обновление — раз в 4 секунды при открытой
вкладке браузера. Значения вне рабочего диапазона, статистические отклонения и пропуски
требуют проверки; жёлтый цвет сам по себе не означает доказанную аварию.

Карточки узлов обновляются на месте: раскрытие полей и прокрутка JSON сохраняются.
Потоки различных запусков, источников и WS-сессий имеют отдельные истории анализа.
Численные пределы предупреждений перечислены в `agent/src/kupol/dome/monitoring.py`; это рабочие
эвристики, а не пороги аппаратной защиты. Для фонового статистического сравнения
нужно минимум 12 различных отсчётов; пороги и пропуски проверяются сразу.

Плановый обзор LLM — раз в 180 секунд по умолчанию (меняется в панели или через
TRIGGER_REVIEW_S); любой другой вызов модели сдвигает таймер. Числовые предупреждения идут
поводом `numeric` с низким приоритетом. Без свежих данных результаты команд не считаются
подтверждёнными — это проверяет код (Gate, диспетчер, итог требования Оператора).

Оперативные сценарии `OS-*` (ложные, скрытые, каскадные и прямые воздействия) входят в RAG
Купола (`rag/data/knowledge_base/operational_scenarios.json`) и попадают в промпт обычным
поиском RAG. Форматы: [контракт наблюдения](../contracts/telemetry-monitoring.md).
