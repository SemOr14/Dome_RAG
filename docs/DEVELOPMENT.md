# Параллельная разработка

Решение команды от 26.10.2026: SemOr14 отвечает за БД и API, другой участник — за агентную систему. Разработка идёт изолированно, затем результаты сливаются через pull request в `main`.

| Ветка | Область изменений | Результат |
|---|---|---|
| `work/data-api` | `services/data_api/`, документация БД, импорт исторических данных | Сохранение, запросы, журнал всего входа/выхода |
| `work/agent-system` | `agent/` | Решения, управление Куполом, симулятор, панель, клиент записи событий |
| `main` | `contracts/`, общие данные и документация | Согласованная основа обеих веток |

Перед работой: `git fetch origin`, переключиться на свою ветку. На каждом компьютере — отдельная рабочая копия; не открывать одну общую папку с двумя процессами Git. Два участника не редактируют одновременно одни файлы.

## Граница интеграции

Агент остаётся единственным владельцем подключения и команд к Куполу. БД/API принимает копии событий через `POST /v1/events` или пакетный `POST /v1/events/batch`. Самостоятельное управление оборудованием из сервиса хранения в первую версию не входит.

Агент создаёт `run_id` на запуск и новый `session_id` на каждое WebSocket-соединение. Каждое сообщение и лог получает устойчивый `event_id`; повторная доставка использует тот же ID. `request_id` сохраняется с исходным JSON-типом. Для пары запрос/ответ нужны `run_id + session_id + request_id`, потому что счётчики запросов после переподключения могут повторяться.

Точки подключения записи у агента: отправка auth и любого запроса; получение auth_response, любого ответа, телеметрии и чата; неизвестные сообщения; ошибки разбора, таймауты, переподключение; все записи журнала агента и запросы/ответы LLM. Ключи в auth, HTTP-заголовках и текстах скрываются до хранения.

При недоступности БД агенту нужен локальный журнал исходящих событий и повторная доставка с теми же `event_id`. Подтверждение записи — ответ API после фиксации транзакции. Это интеграционная задача разработчика агента; при импорте архива такой клиент ещё не подключался.

## Порядок слияния

1. В своей ветке описать задачу и изменяемые пути.
2. Общие контракты менять отдельным небольшим pull request; не копировать их независимо в оба приложения.
3. Перед слиянием обновить свою ветку из `main`, выполнить проверки своего компонента и проверить контрактные примеры.
4. В pull request указать формат входа/выхода, миграции и результаты проверок.
5. После слияния обе ветки обновляются из `main`.

## Ближайшие задачи

- БД/API: схема событий, исходные JSON-сообщения, все снимки узлов, API чтения/записи, журнал HTTP входа/выхода, импорт JSONL.
- Агент: интеграция клиента записи без потери сообщений, повторная доставка, проверка реального каталога прав и параметров команд.
- Вместе: проверка цепочки `решение → исходящая команда → ответ → новая телеметрия → проверка эффекта`.

Архивный бенчмарк относится к mock-LLM и симулятору; он не подтверждает работу на реальном оборудовании.
