### Как реализованы задания 0–6 в сборке

**Контракт и режимы.** История не является управляющим API. По умолчанию competition/history, recommendation и включённые алгоритмы; старт не подключает оборудование. Автор команды хранится как operator/algorithm/agent/safety в совместимом metadata.actor. Смена режима/сессии меняет policy_epoch. Старые ответы модели не исполняются.

**Уведомления.** Панель и meeting_01; без новых каналов. Ack означает получение обращения, не устранение причины, reset интерлока или разрешение resume. Красный риск не понижается текстом модели. Старые восстановленные факты не выдаются за текущие.

**Производство.** У двух карточек есть свежесть, текущий файл, состояние/hold/error, последнее воздействие, progress/elapsed/ETA. Машинные/рабочие координаты ЧПУ подписаны отдельно. operation_id защищает от повторного клика/HTTP. ETA прежде всего из телеметрии, иначе маркированная оценка по нескольким устойчивым точкам; неизвестное остаётся неизвестным.

**Upload.** Только принтер, готовый UTF-8 G-code до 16 МБ, разрешённый SHA-256 и безопасное имя; нельзя перезаписывать выполняемый файл. Серверный хеш может отсутствовать: удалённая побайтовая идентичность тогда не доказана.

**Границы API.** Нет вымышленной паузы/отмены станков, upload ЧПУ, прямого Klipper/GRBL/SSH/serial, CAM/слайсинга, потоковой отправки, дробления УП и восстановления ЧПУ по координатам. Питание не выдаётся за pause.

**Жёлтая.** Выключает ИИ/обычные правила и отменяет планы сразу, не ждёт LLM. В service/full выполняет один ограниченный план второстепенных линий 1,2,3,4,5,6,8. Линия 7, критические и нужные переходные охлаждение/вытяжка сохраняются. Смешанная линия 1/неизвестная продувка могут дать partial. Нет отдельного latch/reset; возврат обычными режимами/ручными командами. line_on/смена режима отменяют конфликтующий хвост.

**Красная.** Закрывает всё наше приложение через launcher, включая зависшие worker/потоки и переподключение, с ограниченным flush. Сервер Купола не завершается; оборудование этой кнопкой не обесточивается. Повторный python run_panel.py — обычный старт без red_latch. Внешний Restart=always противоречит намеренному выходу; приложен пример systemd.

## 3. Подробно: как проходит маршрут

### 3.1. Что здесь называется алгоритмом

Это детерминированный Python-код, который по текущим значениям и памяти эпизода возвращает **Intent**:
- ситуация, причина и свидетельства;
- приоритет и cooldown;
- последовательность Step: устройство, действие, значение, ожидаемый эффект Expect;
- сообщение/запрос человеку, если нужен.

Сам плейбук не пишет в сокет. Он предлагает намерение Runner, а каждый Step проходит Gate. Основные механизмы: пороги, сравнение независимых источников, медиана/выбросы/скорость, взвешенная эвристическая оценка, таймеры устойчивости, состояния эпизода, бюджеты попыток и проверка нового результата. ИИ — отдельный исполнитель анализа, а не часть этих if/таймеров.

### 3.2. Точный порядок одного такта Runner

1. Runner читает уже полученный кадр клиента, обновляет DomeState, каталог и новый чат. При первом запуске исторический чат отмечается без исполнения старых заданий.
2. Gate проверяет pending ранее отправленных команд. Новый кадр должен продвинуть состояние и updated_at целевого узла. Просто повторить прежнее значение в локальном такте недостаточно.
3. Успешный шаг разрешает зависимый хвост плана только при той же сессии и допустимой политике. Ошибка/таймаут проверки/смена сессии останавливают хвост.
4. Обрабатываются сервисные ручные намерения. Competition этот прямой путь отклоняет.
5. classify_live обновляет инциденты критичности/недоступности независимо от здоровья ИИ. Это не ожидание ответа модели.
6. route_playbooks вызывает включённые плейбуки, собирает Intent, покрытые узлы, сводку, обработанные id чата и исключения Python. При algorithms_enabled=false обычные плейбуки пропускаются.
7. Прямой автоматический resume принтера из старого ResumePlaybook отфильтровывается. Добавляется результат отдельного PrinterSupervisor, когда наступил его период.
8. Намерения сортируются по числовому priority: меньше — раньше. Каждый шаг исполняется через Runner.execute → Gate.submit → единый DomeClient.
9. Если ИИ включён/настроен/здоров и роль team, Dispatcher рассматривает события. В модель передаётся сводка предложений плейбуков; реальные отправки/проверки видны в журнале. Вызов идёт в фоновом потоке.
10. Перед применением ответа снова сверяются policy_epoch, session_id, включённость ИИ, остановка процесса и, для resume, тот же файл. Затем машинная валидация и Gate.
11. IncidentCenter доставляет неотправленные обращения через общий Gate; наблюдение/состояние сохраняются.

Этот порядок — не один бесконечный цикл «правила ↔ модель». Переходы ограничены фактами, поколением политики, дедупликацией и бюджетами.

### 3.3. Когда алгоритм решает сам

Известный случай с достаточными данными: например, низкий SOC и доступная сеть, пригодное расхождение CO₂, корректный одиночный запрос запуска. Плейбук создаёт конкретный шаг и Expect. При успешном допуске и новом подтверждении действия ИИ для этого типового изменения обычно не нужен.

Покрытие отмечается как **covered_nodes**. Для большинства телеметрических поводов Dispatcher отбрасывает повторный анализ, если все их узлы уже покрыты. Это эвристика узла, не точная идентичность incident/job/rule/episode. Наличие Intent само по себе не является доказательством физического устранения причины.

### 3.4. Когда управление анализа переходит к ИИ

| Повод | Как появляется | Что получает модель |
|---|---|---|
| Непокрытая аномалия/конфликт/stale | Телеметрический детектор Dispatcher | Новый факт и связанные узлы/контекст |
| Непонятный вопрос/требование | Новый id Оператора, не обработанный правилами; либо запрос панели | Текст запроса и состояние |
| Исключение плейбука | RouteResult.failures → playbook_failure_trigger | Имя правила, тип ошибки, сводка и текущие данные |
| Отказ локального Gate | gate_rejection_trigger | Предложенная команда и причина запрета; обход/повтор запрещены |
| Отказ Купола | gate_action_trigger, success=false | Узел/действие/значение и upstream error |
| Нет ответа после отправки | gate_action_trigger, timeout | Итог неизвестен; сверять эффект, не повторять вслепую |
| Команда принята, эффекта нет | gate_verification_trigger, ok=false | Expect, наблюдаемое, action seq и запрет повторения |
| Позднее подтверждение после таймаута | verification, ok=true для timed_out | Неопределённость закрыта, повторять не нужно |
| Плановый обзор | trigger_review_s и отсутствие других pending | Обзор без обязательного воздействия |

Командные/operator/verification поводы не подавляются covered_nodes. «Сразу» означает создание явного повода; сетевой вызов модели всё равно ждёт завершения предыдущего анализа и ограничения частоты.

По умолчанию Dispatcher: минимальный интервал 10 с, cooldown повторного повода 120 с, обзор 900 с; переменные окружения меняют эти значения. Это настройки кода, не физические нормативы. Тик supervisor 12 с не означает вызов DeepSeek каждые 12 с.

### 3.5. Что делает ИИ

Собираются повод, свежая телеметрия/каталог, журнал решений/действий/проверок, граф влияний и релевантный RAG. История/RAG — контекст, а не измерение текущей причины или право выполнить команду.

Модель возвращает структурированный JSON: situation/cause/evidence, actions, operator_message, request_human, wait_and_watch и ссылки RAG. llm_agent/validate.py проверяет структуру, каталог/права и жёсткие правила. Адаптер to_intent допускает **один первый разрешённый управляющий шаг**; последующие предложения откладываются до нового решения по телеметрии. При red request_human опасные исполнительные шаги в Intent не переносятся.

Модель не получает универсальный shell/SQL/network-инструмент и не присваивает confirmed. Оценка модели не отменяет запрет Gate.

### 3.6. Что именно проверяет Gate

В порядке допуска: политика/epoch, ссылка на decision, роль team, возраст последней телеметрии, текущий describe_nodes, локальная allowlist, типы/диапазоны значений, чат-лимит, pending на узле, недавний no_effect, лимиты переключений линии и состояние конкретного действия.

Перед сетью после общего лимитера повторяются актуальные ограничения. Нельзя открыть бокс при печати/неизвестной температуре; start требует свободный станок, существующий файл и homed; принтер дополнительно bed_clear=true. Дым запрещает старт/движение и включение производственных линий. E09 и IL_OVERCURRENT не сбрасываются по одной погоде/таймеру.

Запись намерения и бюджетов сохраняется **до сети**. При ошибке обязательного сохранения команда отклоняется. Один управляющий транспорт; confirmed=true не обходит эти проверки.

### 3.7. Как доказано выполнение

| Статус | Что означает | Следующее действие |
|---|---|---|
| rejected | Локальный Gate не допустил отправку | Анализ причины; запрет не обходится |
| dry_run | В сеть не отправлено | Не объявлять аппаратное выполнение |
| sent / accepted | Купол принял запрос | Ждать отдельную проверку эффекта |
| ambiguous | Отправка могла состояться, ответа нет | Сверка, без автоматической повторной команды |
| verified | Новый кадр/время узла и Expect совпали | Можно продолжить допустимый хвост плана |
| no_effect | До дедлайна новое подтверждение не получено | Остановить зависимые шаги; ИИ или человек по автору/режиму |

Обычный verify_timeout_s — 20 с, отдельные Expect могут задавать другой срок. Для resume Gate усиливает ожидание: исходное условие + **то же имя файла + числовой прогресс больше исходного**, с таймаутом не меньше 45 с. Состояние PRINTING само по себе недостаточно. Никакого exactly-once стороннего станка эти проверки не обещают.

### 3.8. Когда вызывается человек

Прямо, без обязательного ИИ: дым/критический риск, физическая причина, FILAMENT_RUNOUT/BED_COLLISION, неприемлемый ALARM/lockout, потеря задания/питания/координат и допустимые случаи ручного осмотра. classify_live и supervisor могут создать инцидент независимо от модели.

После попытки алгоритма: если ИИ выключен/недоступен, невалиден, не предложил допустимого шага, не смог исполнить предложение либо сам запросил человека. Ошибка **действия ИИ** идёт человеку, а не обратно в новый такой же ИИ-цикл. В recommendation предложение после ошибки также требует человека.

Пример формата, не живое событие:
```json
{
  "situation": "Принтер удержан по FILAMENT_RUNOUT",
  "actions": [],
  "request_human": {
    "node_id": "printer_3d_01",
    "incident": "Требуется замена филамента",
    "severity": "red",
    "facts": [
      {"node": "printer_3d_01", "param": "hold_reason", "value": "FILAMENT_RUNOUT"}
    ],
    "already_done": ["Причина удержания прочитана", "Автоматический resume не выполнялся"],
    "required_action": "Замените филамент и проверьте принтер по штатной процедуре."
  }
}
```

Runner.execute превращает request_human в сохраняемый инцидент. Для внутреннего handoff _human_review создаёт action:node:action либо routing:playbook. Панель показывает причину/факты/действие; meeting_01 получает уведомление через общий Gate. History-only/сбой доставки видны как недоставка.

Человек нажимает «Принял»: open → acknowledged. Это не resolved, не устранение физической причины и не сброс аппаратного интерлока. Возврат после жёлтой не требует отдельного reset.

### 3.9. Как исключаются гонки и зацикливание

| Механизм | Что останавливает |
|---|---|
| policy_epoch + session_id | Позднее решение старого режима/соединения |
| Блокировка узла и pending | Одновременные несовместимые команды алгоритма/ИИ/человека |
| operation_id | Повторный HTTP/клик для одной производственной операции |
| Gate resume budget | Повтор пустых resume одной причины |
| no_effect cooldown | Слепую такую же команду после неполученного эффекта |
| Ключ причины/эпохи в Brain | Повторный анализ одного нерешённого локального отказа каждый тик |
| handled_message_ids | Повтор исполнения известного сообщения в правилах и ИИ |
| Исторические id при старте | Автоматический replay старого приказа из чата |
| Единственный владелец resume принтера | Гонку старого ResumePlaybook и supervisor |
| external_verification | Второй модельный таймер поверх проверки Gate в Runner |
| Исключение meeting_01 из feedback | Цикл «ошибка сообщения → ИИ → ещё сообщение → ошибка» |

Ограничение: это набор фактических механизмов, **не полный сохраняемый автомат арбитража каждого события**. После удаления старой записи дедупликации/нового эпизода может потребоваться новый анализ. Не все старые say/operator_message превращены в одинаковый HumanEscalation.

### 3.10. Влияние выбранного режима

| Режим | Обычные плейбуки | ИИ | Аппаратные команды ИИ |
|---|---|---|---|
| recommendation + algorithms=true | Работают через Gate | Анализирует | Предложение, без автоматического исполнения |
| autonomous + algorithms=true | Сначала правила | Затем события/ошибки | Допустимы через тот же Gate |
| off + algorithms=true | Работают | Новых вызовов нет | Старые результаты обесценены |
| off + algorithms=false | Нет обычного управления/авторезюмирования | Нет | Нет |
| manual_after_yellow | Обычные правила выключены | Выключен | Только отдельный разрешённый safety/ручной service-путь |
| shutting_down | Исполнение прекращается | Новых вызовов нет | Барьер и выход приложения |

Наблюдение, журнал и инциденты сохраняются при обычном выключении подсистем; красная завершает и их процессы. Аппаратной защитой самого Купола приложение не владеет.

## 4. Подробно о каждом алгоритме

Порядок вызова default_playbooks: **smoke → co2 → condensate → resume → tasks → printer → energy → overcurrent → phantom → alarms → stale → clock → network**. После сбора действует priority, поэтому это порядок оценки, не безусловная очередь отправки. Тринадцать плейбуков в основном унаследованы; новые — общий маршрут/политики, supervisor и инциденты.

### 4.1. SmokePlaybook — дым

**Входы:** smoke_detector_01/02, alarm_state/smoke_detected/obscuration_pct, CO/VOC, зона и события автоматики. Считаются свидетельства «реально/ложно» с независимостью по узлу. CO и VOC одного air_quality_sensor не дают два независимых физических источника.

**Правило:** любой положительный признак реальности сохраняет real; для false нужно не меньше двух независимых отрицательных источников. Иначе unknown. Настроены CO ≤5 ppm, VOC ≤150, obscuration ≤3% как признаки отсутствия дыма; это параметры локального кода.

**Предложение старого плейбука:** при false он может сформировать acknowledge события, reset_alarm и позднее reset IL_SMOKE. **Фактический Gate не допускает отменяющий пожарную реакцию acknowledge IL_SMOKE без проверяемого допуска текущего события/зоны**; такого полного контракта здесь нет. Отсутствие дыма для reset проверяется актуальным измерением. При real/unknown сохраняется защита и требуется осмотр.

**Переход:** classify_live уже открывает красный инцидент без ИИ. Отказ предложенного шага даёт feedback, но модель не может разрешить обход. Поэтому описание «плейбук всегда сам отменяет ложное пожаротушение» было бы неверным.

Источник: playbooks/machines.py, checks.assess_smoke, gate._state_reason.

### 4.2. Co2Playbook — CO₂

**Входы:** три климатических датчика, co2_ppm, доверие, confidence/drift/delay, история изменения, основной датчик и IL_CO2.

**Предварительный отбор:** measurement_usable требует числовой updated_at, пригодный online/status/sensor_state и объявленную задержку 0–30 с. Явные null/отрицательные/NaN задержки непригодны; отсутствие поля в существующем протоколе означает отсутствие объявленной буферизации. 30 с — локальная политика, не закон физики.

**Выброс:** скорость по соседним отсчётам окна 30 с >40 ppm/с — эвристика spike; при трёх источниках два должны отличаться не больше 250 ppm, третий от их среднего — больше 400 ppm. Для false_sensor нужны два оставшихся пригодных хороших источника. Иначе unknown. Реальный рост — минимум два доверенных неподозрительных источника ≥1500 ppm при соответствующей медиане.

**Действия:** пометить подозрительный co2_ppm UNRELIABLE; при необходимости выбрать основной из хороших по score = confidence − |drift|/1000 − delay/100000. Каждый шаг проверяется отдельно. Реальный рост формирует включение/усиление притока и допустимую вытяжку. Старый плейбук прямо предлагает FRESH_AIR. Отдельная полная детерминированная проверка наружной химической/дымовой опасности в этой ветви не реализована; наличие общего Gate не доказывает такой проверки. Это открытый участок согласования правил вентиляции.

**Снятие причины:** для reset IL_CO2 нужны не меньше двух хороших безопасных источников, пригодный основной среди них и значения ниже 1200 ppm; затем новый ARMED. Сам reset не является resume.

**Возврат доверия:** согласие в пределах 250 ppm без новых spike удерживается 600 с; предлагается TRUSTED через Gate. Это не автоматическая калибровка датчика.

**Переход:** при недостатке свидетельств защита сохраняется. Unknown может быть покрыт самим Intent плейбука и потому не обязан немедленно вызвать ИИ; покрытие узлов — известное ограничение. Исключение/отказ/нет эффекта создают явный feedback независимо от покрытия.

Источник: playbooks/air.py, evidence.py, checks.assess_co2.

### 4.3. CondensatePlaybook — влажность/точка росы

**Входы:** пригодные humidity_pct, temperature_c, dew_point_c трёх датчиков; зазор T−Tросы; доверие и IL_CONDENSATE.

**Правило:** RH >90% либо зазор <1 °C означает «горячий» источник риска. Один такой при двух спокойных — false_sensor; два и больше — real; неполное подтверждение — unknown.

**Действия:** при одиночном подозрительном источнике пометить humidity_pct/dew_point_c UNRELIABLE. При устранённой причине предложить reset IL_CONDENSATE. Gate проверяет минимум два доверенных пригодных источника и известный безопасный зазор каждого; слабое условие старого плейбука не обходит этот допуск.

**Настоящий конденсат:** причина не лечится reset; защита/пауза сохраняются, требуется изменение реальных условий/осмотр. После новых безопасных данных ARMED и продолжение — разные переходы.

Источник: playbooks/air.py, checks.assess_condensate, gate._state_reason.

### 4.4. ResumePlaybook — продолжение станков

**Входы:** hold_reason/level, lockout, интерлок/его pending_s, пригодные измерения, состояние и бюджет попыток.

**Правило:** ALARM/lockout — без resume. FILAMENT_RUNOUT/BED_COLLISION — физическая работа человека. Для IL_* требуется ARMED без pending. IL_CO2 — минимум два пригодных доверенных ниже 1200; IL_CONDENSATE — подтверждённая безопасная влажность. Неизвестная причина не возобновляется.

**Устойчивость:** снятая причина держится минимум 6 с; нет pending resume; локально не исчерпана одна попытка на причину. В старом правиле есть ветви IL_SMOKE/UNDERVOLTAGE, но они не означают автоматический допуск принтера: его resume отфильтрован и принадлежит supervisor. Gate отдельно требует сохранённое задание, homed и прогресс.

**Эффект:** тот же файл, рабочее состояние без удержания, рост прогресса. Отправка «проверочного resume» не применяется. Это не восстановление ЧПУ по сохранённым координатам.

Источник: playbooks/machines.py, Runner.tick, Gate.continued_job.

### 4.5. TasksPlaybook — известные команды Оператора

**Входы:** новые operator-сообщения, одно имя .gcode/.nc, серверный список файлов, state, homed, bed_clear, pending.

**Разбор:** простые запросы статуса, выдачи/закрытия бокса, заметки о снятой детали и один именованный start. Известный id отмечается обработанным и не поступает второму исполнителю ИИ.

**Старт:** только немедленный — свободный станок, существующий файл, подтверждённые координаты, свободный стол принтера, нет предыдущей pending-команды. Иначе объяснение отказа **без сохранения задания на будущее**. После освобождения нужен новый запрос с именем файла. Простое «запускай» старое намерение не оживляет.

**Очередь удалена:** queued/waiting_confirm из старого jobs отбрасываются, starting/started переходят только в active_jobs-наблюдение. Несколько файлов в одной реплике и второй start одного станка в кадре отклоняются. Наблюдение завершения не запускает следующий файл.

**Переход:** непонятный новый вопрос может уйти в ИИ. Ведётся память уже начатого, не очередь планируемых файлов. Старая история при запуске не исполняется.

Источник: playbooks/tasks.py, Runner._collect_chat.

### 4.6. PrinterPlaybook — завершение и бокс

**Входы:** state/real_state/webhook_state, progress/time_left, температура стола, hold, замок/дверь и bed_clear.

**Правило:** webhook COMPLETED подозрителен, если state/real_state ещё PRINTING, progress <99% или time_left >60 с. done требует state COMPLETED и согласованного real_state, отсутствия такого конфликта и известного progress ≥99% либо отсутствующего progress по старой проверке. Поэтому Gate независимо проверяет допуск открытия.

**Действия:** не открывать при печати/паузе/неизвестной температуре; дождаться стола <40 °C. После наблюдавшейся печати и подтверждённого завершения предложить unlock замка 0 и сообщение. После снятия детали, закрытой двери и bed_clear=true — relock. Открытый замок при печати вызывает предложение блокировки.

**Переход:** противоречивый webhook не является причиной начать новый файл или считать изделие готовым. Новое завершение/свежесть проверяет код, не одна строка модели.

Источник: playbooks/production.py, checks.assess_printer, Gate.

### 4.7. EnergyPlaybook — питание/генерация

**Входы:** SOC, режим инвертора, наличие сети, PV/load/battery power, ошибки, MPPT, освещённость.

**Пороговый автомат:** HYBRID + SOC <35% + доступная сеть → GRID_ONLY; GRID_ONLY + SOC ≥70% + PV ≥300 W → HYBRID. Между переключениями не меньше 600 с. При низком SOC без сети — предупреждение о дефиците, не произвольное обесточивание.

**IL_LOAD_SHED:** низкий/неизвестный SOC сохраняет разгрузку; при восстановлении не ниже 35% предлагается reset через Gate. Прогноз до критических 25% — оценка по энергии/разряду; в старом расчёте возможна резервная ёмкость 2,5 кВт·ч, это не измеренная ёмкость установки.

**MPPT:** при освещённости ≥2000 лк и отсутствии ошибки предлагается включить выключенные каналы/инверторный MPPT.

**Ошибка E09:** автоматический reset по высохшему воздуху/таймеру удалён; нужна проверка изоляции человеком. Оставшиеся старые параметры humidity_ok_pct/reset-gap в YAML не означают действующую процедуру сброса E09.

Источник: playbooks/energy.py, checks.assess_energy, gate._state_reason.

### 4.8. OvercurrentPlaybook — перегрузки/защита линий

**Входы:** IL_OVERCURRENT, shed_lines, state/protection_state линии и память срабатываний.

**Старое предложение:** после 180 с плейбук способен предложить один reset; повтор в пределах 900 с ведёт к сообщению о реальной перегрузке. TRIPPED/RCD_TRIP/RCD_TRIPPED вызывают просьбу проверить нагрузку.

**Фактическая политика сборки:** Gate блокирует reset IL_OVERCURRENT, потому что таймер не доказывает устранение перегрузки. Нельзя описывать это как работающий автоматический возврат любой линии. Отказ попадает в явный feedback ИИ, который не может разрешить тот же запрещённый reset.

Источник: playbooks/lines.py и gate._state_reason.

### 4.9. PhantomLinePlaybook — неожиданная нагрузка резерва

**Входы:** настроенные резервные линии, ON, power_w и память времени.

**Правило:** по умолчанию линия 8, мощность не ниже 20 W непрерывно 120 с. Это эвристика «на резерве не должно быть нагрузки», не доказательство причины утечки.

**Действие:** line_off с Expect линии OFF, затем просьба осмотреть клеммник/влагу. Cooldown намерения 3600 с. Линия 7 не входит в резерв и не отключается этим правилом.

**Переход:** измеренное отключение проверяется Gate; физический ремонт — человек. Если на линии есть фактическая критическая нагрузка, сама конфигурация должна быть сверена до эксплуатации.

Источник: playbooks/lines.py.

### 4.10. AlarmPlaybook — аварии устройств

**Узлы:** приточная вентиляция, вытяжка FabLab, охлаждение, насос.

**Правило:** alarm=true → ограниченный штатный reset_alarm; минимум 300 с между попытками, по текущей настройке не больше 3 в час на узел. Проверяется alarm=false; после недавнего сброса выключенному устройству может предлагаться turn_on с Expect ON/enabled.

**Особая ветвь:** MOTOR* вытяжки сначала вызывает просьбу почистить/продуть фильтр. Это физическая проверка. При повторяющихся авариях — прекратить сбросы и просить осмотр.

**Ограничение:** старый плейбук опирается на память/таймеры и сообщения; отдельного сохраняемого подтверждения «фильтр очищен» для всех таких переходов не реализовано. Не объявляется универсальным безопасным восстановлением любой механической аварии.

Источник: playbooks/devices.py.

### 4.11. StalePlaybook — устаревшие/недоступные узлы

**Входы:** frozen_nodes, online/status, updated_at и продвижение измерений. Порог узла — 30 с по конфигурации; общий Gate дополнительно ограничивает возраст последнего кадра 20 с.

**Действие:** предложить reconnect только если оно есть в каталоге; не чаще 300 с и максимум 3 за 1800 с. Expect — данные узла снова обновляются. Старые показания не становятся нормой.

**Переход:** критичность недоступности отдельно определяет classify_live с учётом узла/активного задания. Отказ/нет эффекта reconnect передаются анализу/человеку. ИИ не создаёт новое измерение из предположения.

Источник: playbooks/devices.py, state.py, incidents.classify_live.

### 4.12. ClockPlaybook — время вычислительного узла

**Вход:** edge_compute_01.clock_offset_s.

**Правило:** при числовом |offset| ≥2 с предлагается штатный sync_time. Заявленный Expect — |offset| <1 с на новом состоянии, cooldown 600 с.

Это коррекция часов узла, не разрешение переупорядочить исходную историю или считать время БД временем физического измерения. Проверка общих источников и полнота всех legacy-Expect не объявляются окончательно доказанными.

Источник: playbooks/devices.py.

### 4.13. NetworkPlaybook — связь

**Входы:** network_link_01.link_state, packet_loss_pct, flaps и признак patchcord_replacing.

**Правило:** link != UP либо потери ≥30% держатся 30 с; если патчкорд уже меняют, повтор не нужен.

**Действие:** сообщение Оператору о физическом переключении на резерв; не программное переключение несуществующего реле. Cooldown 1800 с. Команды при неопределённой доставке не повторяются вслепую.

Источник: playbooks/devices.py.

### 4.14. PrinterSupervisor — отдельный надзор принтера

Это новый серверный цикл поверх уже поступившей телеметрии, не ещё один транспорт. Период 10–15 с, по умолчанию 12; одинаковый updated_at не считается новым доказательством.

1. Проверяет свежесть, online, питание линии 3, homed, состояние/real_state, файл, pause/hold, progress/elapsed.
2. Во время PRINTING запоминает active_file, running_stamp и продвижение прогресса. Новый файл/сброс elapsed начинают новый эпизод.
3. Неизменный процент за один тик не является stall. Необязательный stall_timeout_s по умолчанию не задан; HEATING/HOMING/PREHEATING исключаются из этого сигнала.
4. Потеря питания/координат/задания после активной работы ставит unsafe_restart и зовёт человека. IDLE/ABORTED не превращаются в новый start.
5. Ручная/неизвестная пауза, IL_SMOKE, UNDERVOLTAGE, FILAMENT_RUNOUT, BED_COLLISION, ALARM и иная неизвестная причина не возобновляются автоматически.
6. Для автоматики допустимы только IL_CO2/IL_CONDENSATE; нужны включённые алгоритмы, то же ранее наблюдавшееся задание, отсутствие manual/operator/emergency pause_origin, pending и уже использованной попытки.
7. cause_cleared должен подтвердиться на разных новых метках узла; затем запись resume_sent сохраняется до выдачи намерения.
8. Один resume проходит Gate; он требует тот же файл и рост прогресса. Неподтверждение вызывает красный инцидент, не вторую/третью попытку.

Открытие бокса и завершение остаются за PrinterPlaybook/Gate. Supervisor не делает CAM, home-последовательность или восстановление из середины G-code.

Источник: printer_supervisor.py и Gate.continued_job.

| Конденсат | RH >90% или T−Tросы <1 °C | checks.py |
| Взвешенная уверенность | p=1/(1+exp(−2,5·S)), S — сумма весов real минус false | checks.p_real |
| Независимость | Число разных node, а не разных полей одной платы | checks.independent_sources |
| Проверка эффекта | Новый кадр/updated_at + Expect; обычный дедлайн 20 с | Gate |
| Resume | Тот же файл и рост progress, минимум 45 с на проверку | continued_job |
| Лимиты отправки | Общий клиент 4 запроса/с по YAML; чат 4 сообщения/10 с | dome.yaml |
| Лимит линии | 2 переключения за 120 с | Gate |
| После no_effect | Та же команда заблокирована на 120 с | Gate |
| Вызов ИИ/обзор | Не чаще 10 с, cooldown повода 120 с, обзор 900 с по умолчанию | llm_agent/config.py |
| Надзор принтера | 12 с, диапазон 10–15 | supervisor |
| ETA | Телеметрия либо устойчивая оценка по нескольким точкам progress | integration/production.py |

p_real — эвристическая агрегированная уверенность, не калиброванная статистика отказов и не самостоятельный допуск. Пороги из текущего файла, особенно помеченные ASSUMPTION, требуют проверки на установке. Фильтр measurement_usable применён прежде всего в сверках CO₂/влажности и соответствующих Gate-проверках; его наличие не означает, что каждый старый плейбук одинаково проверяет каждый исходный датчик.

RAG использует BM25/локальные эмбеддинги для поиска контекста. DeepSeek формирует диагностическое предложение. Эти механизмы не подменяют перечисленные пороговые алгоритмы управления.

## 6. Примеры полного прохождения

### А. Один CO₂-датчик резко показывает 3000, два пригодных — около 800 ppm

Co2Playbook проверяет не только числа, но качество/задержку/независимость. При подтверждённом выбросе предлагает UNRELIABLE, затем смену основного при необходимости. Каждый шаг ждёт нового эффекта. При отказе Gate возникает командный trigger ИИ; ИИ может предложить иной допустимый шаг или request_human, но не выдать тот же запрет за разрешение. Если два «800» пришли с задержкой 900/1800 с, пример перестаёт быть доказанно ложной тревогой: unknown и сохранённая защита.

### Б. CO₂ реально высокий на нескольких пригодных источниках

Правило предлагает допустимую вентиляцию; IL_CO2 не сбрасывается ради продолжения. Только после новых безопасных данных ниже порога, reset → ARMED и проверки может возникнуть отдельное восстановление сохранённого задания. Оператор/ИИ не объявляют реальную причину устранённой общими словами.

### В. Конденсат: один источник опасный, два спокойные

Сначала проверяется приборная пригодность и T−Tросы, затем подозрительные параметры отмечаются. Reset проходит отдельный Gate с минимум двумя подтверждёнными безопасными источниками. При недостатке данных нет «успешного сброса по догадке»; отказ анализируется и при необходимости передаётся человеку.

### Г. Принтер PAUSED из-за IL_CO2, причина ушла

Supervisor уже должен был наблюдать тот же файл в работе. На новых метках подтверждаются снятая причина/ARMED, питание и координаты. Сохраняется одна попытка, отправляется resume. Только новый кадр с тем же файлом и выросшим progress подтверждает продолжение. ACK без роста → no_effect/инцидент, повторного resume нет.

### Д. FILAMENT_RUNOUT или потеря питания

Путь идёт человеку: заменить/осмотреть и выполнить штатную процедуру. Промежуточный DeepSeek для физической замены необязателен. Нет автоматического reset/start с начала файла; ack инцидента не доказывает замену.

### Е. Купол не ответил на команду

Результат ambiguous, создаётся повод анализа и ожидание эффекта. Модель не повторяет команду «для проверки». Позднее verified закрывает неопределённость и может сформировать resolved-trigger; отсутствие эффекта до дедлайна — новая причина эскалации. Если это уже был шаг ИИ, повторный круг ИИ не создаётся.

### Ж. Занятый станок и просьба запустить следующий файл

TasksPlaybook отвечает отказом без очереди. Освободившийся станок сам файл не запускает; нужно новое именованное намерение. Старое «запускай» или историческая реплика после рестарта недостаточны.
