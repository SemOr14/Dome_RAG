# Управление производством — локальный контракт v1

База: `7292ae75eecac56cb9f4bca12f335504559a2af3`. Новые feature-ветки основаны на одном
контрактном коммите. Межкомпонентные изменения для интеграции: Runner/Gate/Client проверяют
`ControlPolicy`; Hub владеет серверным режимом; UI обращается только к Hub; события сохраняются
через существующий envelope/Store. RAG и исходные записи не изменяются.

Профиль задаётся сервером: `DEPLOYMENT_PROFILE=competition|service`. Объём API:
`DOME_API_SCOPE=history|full` (до уточнения владельца — history). История не подтверждает текущее
состояние, не предоставляет upload/start/control и отправку в meeting_01.

AgentMode: off/recommendation/autonomous; algorithms_enabled независим. Каждая смена режима
увеличивает policy_epoch, отменяет несовместимые несостоявшиеся отправки и хвост жёлтого плана.
`confirmed=true` не отменяет Gate, профиль, capabilities, свежесть и ревизию политики.

OperatingState: normal/manual_after_yellow/shutting_down. manual_after_yellow — отметка события,
не блокировка. shutting_down только в памяти завершающегося процесса. Перезапуск не требует reset.

Команда: operation_id, causal_event_id, actor (operator/algorithm/agent/safety), policy_epoch,
agent_mode, run_id/session_id, sent/accepted отдельно от verified. Совместимость: автор нового
типа хранится в metadata.actor, существующие source остаются прежними. Таймаут после отправки
— ambiguous, сверка текущего задания, без автоматического повтора. Exactly-once не обещается.

EquipmentCapabilities, ProductionJob, Incident определены в kupol.dome.control. Неизвестная
capability выключена. Источник ETA и время измерения обязательны; один job — один файл, без очереди.
Инцидент: open → acknowledged → resolved; ack не разрешает resume и не сбрасывает интерлок.
Проекции восстанавливаются из новых event_type существующего журнала, миграция исходных записей
не нужна. Секреты редактируются существующим Redactor; REST наследует авторизацию и HTTP-аудит.

Примеры переходов:

```json
{"agent_mode":"off","algorithms_enabled":true,"policy_epoch":1}
{"agent_mode":"off","algorithms_enabled":false,"policy_epoch":2}
{"operating_state":"manual_after_yellow","agent_mode":"off","algorithms_enabled":false,"policy_epoch":3}
{"agent_mode":"autonomous","algorithms_enabled":true,"operating_state":"normal","policy_epoch":4}
```

Красная увеличивает ревизию и завершает все процессы приложения. Следующий обычный запуск
использует обычные стартовые настройки. Старые неподтверждённые действия сверяются без переотправки.
Линия 7, критические узлы и необходимые переходные охлаждение/вытяжка сохраняются при жёлтой;
линия 1 смешанная. Подробная политика отключения реализуется отдельной feature-веткой.

## Дополнение 1.1: ошибки маршрутизации и одиночные задания

- `RouteResult.failures` явно передаёт исключение плейбука в диспетчер ИИ. При выключенном/
  недоступном ИИ, ошибке самого анализа или неудаче предложенного ИИ действия вызывается человек.
- Отказ, таймаут и проверка эффекта Gate связаны по action seq; неподтверждённая отправка не
  повторяется. Ошибка доставки сообщения в чат не запускает рекурсивный вызов модели.
- Покрытие узла плейбуком не подавляет триггеры исхода команды/ошибки алгоритма. Одинаковая
  нерешённая причина не отправляется ИИ каждый тик; смена режима обесценивает её результат.
- Обработанные правилами сообщения отмечаются по конкретным id, без пропуска более раннего
  непонятного сообщения. Одно сообщение не исполняется одновременно правилами и ИИ.
- `TasksPlaybook` принимает один файл только для немедленного запуска. Занятость, занятый стол,
  неизвестные координаты и отсутствие допуска означают отказ без отложенного старта. После
  исправления требуется новая явная команда с именем файла. Старые queued/waiting_confirm записи
  удаляются; записи начатого задания сохраняются только для наблюдения, не для повторной отправки.


## Дополнение 1.2: политика безопасности, 27.10.2026

- `prompts/safety.md.j2` — обязательная политика системного промпта основного агента и старого
  советника. Рекомендации алгоритмов и RAG не отменяют её. Gate сохраняет независимую проверку.
- Разные node_id не доказывают независимость. Для исключения климатического источника и снятия
  климатической защиты требуются свежие сопоставимые источники одной зоны/группы с явно заданными
  различными `failure_domain`. Неизвестная топология не дополняется догадками. Это необязательная
  существующая метаинформация исходной записи; новых полей или команд wire API не добавляется.
- Сброс неизвестной физической/электрической аварии, автоматическое снятие пожарной реакции,
  возврат нагрузки по одному SOC и автоматическое восстановление доверия к неисправному источнику
  запрещены: текущий API не предоставляет проверяемого допуска/процедуры. Нужен Оператор.
- После неуспеха/неподтверждённого эффекта команда удерживается в `failure_holds` локального
  runtime checkpoint. Истечение cooldown и перезапуск не разрешают автоматический повтор.
- Диагностический статус `stabilized` означает только стабилизацию наблюдений. Событие
  `diagnostic_pattern` содержит `incident_closed=false`, `root_cause_status=unverified` и риски.
- Исчезновение симптома/подтверждение команды вызывает `observe_recovery`, сохраняя открытый
  инцидент; в существующем `facts` отмечается `recovery_observed` и необходимость проверки причины.
  `acknowledged` также не закрывает инцидент. Формат Incident и существующие статусы не меняются.
- Внутреннее `resolve(..., review=...)` требует подтверждения состояния, зависимостей и устранения
  причины, evidence, оценки остаточных рисков, последующих действий и автора проверки. Публичного
  endpoint закрытия с таким допуском эта ветка не добавляет; LLM не выдаёт себе разрешение.
