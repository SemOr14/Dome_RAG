# Dome_RAG: устройство системы, API, ограничения и расхождения

Дата анализа: 26 октября 2026 года. Корень материалов: `Dome_RAG-main/Dome_RAG-main` — внутри указанной пользователем папки есть ещё одна папка с тем же названием.

## Главный результат

Это комплект документации, базы знаний и исторических журналов соревнования, а не готовый исполняемый агент или исходный код сервера. Он даёт гораздо более полное описание агентного интерфейса, чем опрошенный ранее HTTP-чатбот. У этих интерфейсов различаются перечни действий и поля; их нельзя объединять как одну подтверждённую версию системы.

В API описаны **37 узлов** и извлечены **103 записи основных управляющих действий** по узлам. Одна запись означает действие конкретного узла; одинаковые названия у разных узлов считаются отдельно. Действительные права выдаёт сервер через `describe_nodes`.

Сопутствующие результаты анализа:

- `Каталог_узлов_по_API.json` — 37 узлов, документированные поля, команды, спецификации значений, правила, интерлоки, исторический перечень полей и отдельно прежние ответы чатбота.
- `Купол_состояния_всех_нод.json` — завершённый последовательный опрос 36 узлов через чатбота, 26.10.2026 с 13:29 до 13:33 по Москве. Это **ответы бота, не прямая WebSocket-телеметрия**.
- `Анализ_исторических_журналов.json` — результат полного разбора всех трёх JSONL-файлов, включая перечни реально наблюдавшихся полей и типов.
- `Индекс_документов.json` — структура всех 19 Markdown-документов с номерами строк и контрольными суммами.

Контрольные команды оборудованию, соединение с сервером соревнования и отправка сообщений Оператору в рамках этого анализа не выполнялись. Примеры клиента из документации не запускались: они включают управление станком и отправку сообщения.

## 2. Как устроено взаимодействие

```text
Программа агента на ноутбуке команды
  ├─ WebSocket → сервер Купола
  │    ├─ auth → роль team или guest
  │    ├─ describe_nodes → действительные права
  │    ├─ telemetry → состояния устройств
  │    ├─ control → разрешённые действия
  │    ├─ query → дополнительные данные / файлы
  │    └─ meeting_01 → задания и сообщения Оператору
  ├─ правила и проверки → быстрые реакции, ограничения, верификация
  ├─ DeepSeek → диагностика и работа с контекстом
  ├─ локальная память/RAG → документация и исторические случаи
  └─ JSONL-журнал → наблюдения, решения, команды и результат

Сервер Купола
  ├─ реальные устройства и их программные обёртки
  ├─ виртуальные узлы / симуляция окружения
  ├─ ПЛК / программные интерлоки
  └─ связь с физическим Оператором
```

Тренировочный день: отдельная виртуальная копия для каждой команды; команда активна. Второй день: реальный Купол, активна команда текущего Оператора. Конфигурации используют один API, но поля результатов реальных и виртуальных устройств могут отличаться.

Физика устройств идёт в реальном времени, сутки окружения ускорены. В API `updated_at` назван Unix-временем часов Купола. Нельзя без проверки считать его часами ноутбука и использовать прямую разность с локальным временем как единственный признак устаревания.

Источники: `01_API.md`, разделы 1–4; `02_Задание_и_оценка.md`.

## 3. Протокол и права

- WebSocket `ws://<выданный хост>:<порт>`, стандартный порт в документации **8765**. Адрес сервера не выводится автоматически из адреса HTTP-чатбота.
- Первое сообщение — `{"type":"auth","key":"<ключ своей команды>"}`; на авторизацию даётся **10 секунд**.
- Роль `team`: телеметрия разрешённых узлов и управление.
- Роль `guest`: только `meeting_01`, без телеметрии инженерных систем и управления ими.
- При смене активной команды приходит `session_revoked`, затем закрытие соединения **4403**. Неверный ключ/отсутствие авторизации — **4401**.
- `request_id` связывает ответ с запросом. Между ответами могут приходить сообщения телеметрии и чата.
- Телеметрия рассылается каждые **2 секунды**, обновление физики/данных описано как примерно **4 секунды**. После команды проверять 1–2 следующих сообщения.
- Не больше **5 команд и запросов в секунду**; чат — не больше **10 сообщений за 10 секунд**.
- **`success: true` = сервер принял команду**, но не доказательство физического выполнения.

`describe_nodes` возвращает `controls`, `control_aliases`, `operator_controls`, `queries`, `service_actions`. Это источник действительных прав; статическая документация может не совпадать с текущими настройками организаторов. `operator_controls` нельзя отправлять как действия агента.

| Файлы | Загрузка через чат не заявлена | Принтер: upload/delete; ЧПУ: загрузки нет, только заранее размещённые файлы |

| ПЛК | Только чтение | Доверие к данным, выбор датчика, сброс/временная блокировка программных интерлоков, квитирование и авторежимы |
| MPPT | Нумерация неизвестна | **1..N** |
| Охлаждение | Диапазон неизвестен | **0–100%**, плюс reset_alarm |
| Радио | Значения неизвестны | **430–440 МГц**, AX25/FSK/LORA/DMR |
| Датчик дыма №2 | Только чтение | reset_alarm для обоих датчиков |
| Резервная связь | Только переключение, значения неизвестны | Канал SATELLITE/LORA/MESH, совместимые протоколы, приоритет трафика |
| Вычислительный узел | Только чтение | Перезапуск сервисов, ограничение нагрузки, синхронизация времени, reboot |

Эти отличия не доказывают, что сервер чатбота и сервер соревнования — одна версия. Правильное действие при подключении агента — получить `describe_nodes`, а не переносить команды из одного интерфейса в другой.

## 5. Производство и ограничения повторов

### Принтер

Документирован Anycubic Kobra 2 Pro, Klipper; имя файла EN4Pro в ответе чатбота не доказывает модель физического принтера.

Команды: `home`, `start_job`, `resume`, `upload_file`, `delete_file`, `set_speed`, `move`. Скорость **50–200%**. Загрузка только подготовленного организаторами G-code, до **16 МБ**. Перемещение после home и вне печати; относительный шаг не более **±50 мм** по оси.

После печати `bed_clear=false`. Оператор забирает деталь через дверь бокса; замком управляет агент. В модели открытие двери Оператором переводит bed_clear в true. Запуск при занятом столе вызывает **BED_COLLISION и ALARM на 20 минут**. Это важное условие модели, а не физический датчик, гарантированно подтверждающий удаление любой детали.

### ЧПУ

Lunyee 3018 Pro Max, GRBL, область **300×180×80 мм**. Команды: `home`, `start_job`, `resume`, `move`, `set_zero`, `probe_z`. Файлы заранее размещены на сервере; загрузки через API нет.

Рабочие координаты: машинные минус `wco_mm`. Перемещения relative/absolute; подача **10–5000 мм/мин**, по умолчанию 1000. Настройка координат и пробинг — в простое без задания.

Пробинг: distance **0.1–30 мм**, feed **1–300 мм/мин**, plate_thickness **0–30 мм**, retract **0–20 мм**, second_pass_feed **1–100 мм/мин**, latch_distance **0.1–5 мм**. Неудачное касание — ALARM:5; результат читать в last_probe, координатах и state.

### Серверное удержание

`hold_level`: null / WARNING / ALARM; `hold_reason` содержит причину. После устранения причины нужно явное resume. Пустые попытки увеличивают `resume_attempts`:

- **3 безрезультатных resume → блокировка на 20 минут**;
- у принтера задание отменяется;
- у ЧПУ сохраняется удержание с остановленным шпинделем;
- при FILAMENT_RUNOUT нужна физическая замена катушки.

Успешно принятая, но не сработавшая resume всё равно может увеличивать счётчик. Нельзя строить цикл «до успеха повторять resume».

## 6. Щит, питание и теплицы

Карта линий: **1 — рабочее место и вытяжка, 2 — бокс ФабЛаб, 3 — принтер, 4 — ЧПУ, 5 — Химлаб, 6 — основной свет, 7 — аварийный свет, 8 — резерв**.

Массив lines индексируется **0–7**, а команды линий — номерами **1–8**. Это разные пространства индексов.

`reset_protection` принимает номер линии; защита перевзводится, линия включается. `line_on` при сработавшей защите отклоняется. Более **3 переключений одной линии за 2 минуты → блокировка на 5 минут**.

ФабЛаб: set_fan_pwm `{fan:0..5,pwm:0..255}`, set_lock `{lock:0..1,locked:boolean}`, set_vacuum 0/1, set_poll_interval **50–5000 мс**. Последний датчик массива — снаружи; остальные внутри. Вентиляторы 0–3 — вдув, 4–5 — выдув.

В общем каталоге узлов описан сценарий коллизии шины: при периоде опроса меньше **500 мс** запись вентиляторов, замков и пылесоса может теряться без ошибки. Следовательно, допустимый числовой диапазон API не равен гарантированно работоспособному режиму в любом сценарии. Проверять `crc_errors`, валидность датчиков и физический эффект команд.

Химлаб: два вентилятора, общий замок, релейный уровень **0–10**; уровень обозначает комбинацию реле, его не следует автоматически трактовать как линейный процент мощности. MQ-2 возвращает ADC/вольты; это не VOC-индекс и не непосредственно ppm.

Дизель дополнительно поддерживает `preheat` на 2 минуты; бак — `transfer_fuel`. Инвертор поддерживает отмену балансировки и режим вентилятора AUTO/ON/OFF. Полные команды и значения включены в JSON-каталог.

## 7. Матрица программных интерлоков

| Интерлок | Условие | Последствие |
|---|---|---|
| IL_CO2 | Основной CO₂ >2000 ppm, 60 с | Удержание обоих станков, приток 100% |
| IL_CONDENSATE | RH >90% либо T−Tросы <1°C, 60 с | Удержание ЧПУ |
| IL_SMOKE | Тревога датчика зоны | Для FABLAB: станки удержаны, L1 отключена; без квитирования через 60 с — пожаротушение зоны |
| IL_LOAD_SHED | SOC <25%, прогноз автономности <1 ч либо дефицит мощности | Сброс линий 8,1, затем 3,4; автозапуск дизеля |
| IL_STORM | Ветер >20 м/с, 30 с | Ветрогенератор выключен, клапаны закрыты, рециркуляция |
| IL_OVERVOLT | Напряжение линии >245 В, 120 с | Отключение линии |
| IL_INV_OVERLOAD | E07 инвертора, 120 с | Отключение линий 8 и 1 |
| IL_HEAT | Инвертор >75°C, 120 с | Отключение L1 |
| IL_OVERCURRENT | Ток >90% заданной уставки, 120 с | Отключение линии |

ПЛК срабатывает по телеметрии, включая ложные значения. Документированы:

- `set_data_trust`: TRUSTED / UNRELIABLE / FAILED, по узлу и параметру, для щита возможно по линии;
- `set_primary_sensor`: climate_sensor_01/02/03;
- `reset_interlock`: перевзведение и возврат отключённых им линий; станки агент продолжает отдельно;
- `block_interlock`: временно, не более 30 минут; `unblock_interlock`;
- `acknowledge`: событие либо all; для дыма отменяет автоматический пуск пожаротушения;
- переключение ventilation_auto и diesel_autostart.

Это разрешаемые **программные** воздействия, а не полномочия обходить независимые аппаратные блокировки. Само наличие команды блокировки не доказывает ложность тревоги. Матрица выше — условия модели по API, не медицинские или электротехнические нормативы для людей.

## 8. Оператор и meeting_01

Этот узел — отдельный общий серверный чат. Он не совпадает с ИИ-помощником на HTTP-странице.

Через него Оператор ставит производственную задачу, а агент сообщает состояние и просит физическое действие. Чат видят все команды; сервер выставляет роль и номер отправителя. Кризисы связи инженерных узлов чат не отключают.

`post_message`: строка либо `{text,name?,to?}`, текст до 4000 символов. `read_messages`: since_id и limit **1–200**, по умолчанию 50. Новые сообщения приходят как meeting_message; последние 10 видны в телеметрии. История сохраняется сервером.

Приоритет задач следует связывать с проверенными сообщениями Оператора и своей сменой; имя агента и произвольный текст сообщения не равны полномочиям отправителя. Очистка истории — администраторская операция.

## 10. Требования к создаваемому агенту

- Однокомандный запуск на ноутбуке команды, дальнейшая работа без интерактивного ввода.
- Переподключение, обработка guest и session_revoked, восстановление после собственного перезапуска.
- Поддержка null, пропавших узлов, устаревших данных, несовпадения полей реального и виртуального устройства.
- Переменные DOME_URL, DOME_KEY, DEEPSEEK_API_KEY, DEEPSEEK_BASE_URL, AGENT_LOG_DIR; секреты не в коде и не в логах.
- Облачная модель — DeepSeek с ключом организаторов; документ называет deepseek-chat и deepseek-reasoner. Это перечень на момент написания, актуальную модель определяет организатор. Локальные модели/эмбеддинги разрешены по этому документу.
- Проверки и быстрые реакции продолжают работать при отказе LLM. Не отправлять всю телеметрию в модель каждые 2 секунды.
- Во время смены управляющие сообщения выдаёт агент; ручные команды участников с ключом команды запрещены по `02_Задание_и_оценка.md`.

Логи: JSONL, немедленный flush, новый файл на запуск, обязательные ts/run_id/seq/kind. Типы: start, stop, connection, observation, decision, action, verification, message, llm_call, error. У action есть ref на decision; после изменения состояния — verification.

Метрики оценивают непрерывность производства, изготовленное изделие, диагностику ложных тревог, упреждение, реакцию, время Оператора, ошибочные и слепые действия, безопасность и качество логов. Конкретных весов в папке нет.

## 11. Противоречия и качество базы знаний

1. **Вентиляция.** knowledge/02_station, 06_microclimate и FAQ говорят, что программного управления вентиляцией нет; API содержит отдельный управляемый узел приточки. Для агента применять текущий describe_nodes и его реализацию, а не общий FAQ.
2. **МС-ТЮК.** В общей справке встречается описание как разветвителя/независимого измерения тока; конкретный API описывает боксы с вентиляторами, датчиками и замками. Нельзя переносить поля между этими описаниями без идентификатора узла.
3. **Состав АКБ.** Общий инвентарь: два LiFePO4 12 В, 150 А·ч, суммарные 300 А·ч без определённой схемы соединения. Бот ранее называл 100 А·ч и 2.56 кВт·ч. Эти сведения не согласованы и не позволяют объявить физическую энергоёмкость известной.
4. **Команды.** В общей энергетике есть описательные SET_LINE/ENABLE_MPPT_CHANNEL и команда ограничения заряда, которых нет в основном каталоге в таком виде. Наличие в справке не равно праву управления.
5. **Роли и ручное управление.** Общая справка допускает различные уровни автономности и ручной резерв; конкретные правила смены требуют полностью автономного агента и запрещают ручные команды. Использовать правила конкретного мероприятия.
6. **Состав команды и модель LLM.** Общая база называет 2–4 участников; ранее предоставленный регламент задаёт другую конкретику. Названия моделей в разных материалах также могут отличаться. Нельзя молча выбирать удобную редакцию; необходима актуальная инструкция организаторов.
7. **Диагностические эвристики.** В микроклимате есть категорические фразы «нет пайки, но растёт CO₂ — датчик врёт» и вывод об отсутствии конденсата только по неизменной температуре. Эти признаки не являются достаточным доказательством; база телеметрии сама требует независимого подтверждения. Не включать их в агент как безусловные правила снятия тревог.
8. **Незаполненные места.** Есть [ЗАПОЛНИТЬ], неустановленные места датчиков, нормы и параметры устройств. Их нужно хранить как неизвестные значения, не дополнять моделью.
9. **История.** knowledge/12_history — преимущественно шаблон, но в Logs есть реальные записи одного прошлого дня. Каталог отказов и расписание прошлого дня не являются сценарием будущей смены.
10. **Аппаратная/программная защита.** Документация отдельно запрещает обход аппаратных блокировок, одновременно предоставляя агенту команды программных интерлоков. Это разные уровни защиты, их нельзя объединять.

Для RAG полезно хранить метаданные source, section, source_line, scope, interface, version/date_if_known и тип сведений: правило, описание, исторический факт, мнение автора, гипотеза, неподтверждённая информация.

## 12. Что ещё нельзя установить из этой папки

- Действительный адрес/порт конкретного сервера команды и актуальные права без подключения к нему.
- Совпадает ли HTTP-чатбот с сервером, описанным здесь, по версии и конфигурации.
- Актуальное физическое состояние 37 узлов напрямую по WebSocket: подключение не выполнялось.
- Полная проводка, гидравлическая схема и подключение вспомогательных потребителей.
- Конкретные файлы и параметры зачётного задания до сообщения Оператора.
- Веса критериев оценки, актуальная редакция разрешённых моделей и деталей допуска.

## 13. Что означает JSON-каталог

В `Каталог_узлов_по_API.json` данные разделены:

- `documented_fields`, `common_fields`, `common_sensor_fields` — поля из документации;
- `canonical_controls_documented`, `control_value_specifications` — статические команды и их значения;
- `specification_markdown` — исходное описание узла, сохраняющее условия и алиасы;
- `historical_field_inventory` — поля/типы, встречавшиеся в 1440 прошлых снимках;
- `chatbot_observation` — отдельно состояние, которое ранее выдал чатбот, с датой получения и пометкой отсутствия независимой проверки;
- `current_websocket_telemetry` — **null**, поскольку прямого опроса сервера соревнования не было;
- `protocol`, `global_rules`, `interlocks` — общие условия API.

У meeting_01 нет нынешнего состояния от чатбота и нет записи в выданной исторической телеметрии. Значения не создавались предположением.
