Документ адресован ИИ-агенту (Claude Code). Задача: с нуля создать рабочий Python-проект, который команда утром адаптирует под реальный API Комплекса «Купол» и использует на зачётной игре.

## 0. Обязательные правила работы (прочитать первыми)

1. **Язык и версия:** Python 3.11+. Весь код на Python, зависимости минимальные и перечислены в `pyproject.toml` (или `requirements.txt`).
2. **Документирование обязательно.** Каждый модуль, класс и публичная функция имеет docstring на русском языке (формат Google style: назначение, аргументы, возвращаемое значение, исключения). Сложная логика поясняется комментариями «почему», а не «что». Типы аннотируются везде (`from __future__ import annotations`, проверка `mypy` не должна падать на `core/` и `adapter/`).
3. **Git обязателен.** В самом начале выполнить `git init`, создать `.gitignore` (Python, `.env`, `logs/`, `__pycache__`). Работать маленькими шагами: **один логический шаг, один коммит**. Сообщения коммитов на русском по схеме Conventional Commits: `feat: ...`, `fix: ...`, `docs: ...`, `test: ...`, `refactor: ...`, `chore: ...`. Не складывать всю работу в один коммит. Перед каждым коммитом запускать тесты; коммитить только зелёное состояние.
4. **Тесты:** `pytest`. Для каждого модуля из `core/` и `adapter/` есть тесты; детерминированные (фиксированный seed у симулятора). Общее покрытие `core/` не ниже 80%.
5. **Ключи и секреты** (API-ключ DeepSeek) только через переменные окружения или `.env`, которого нет в git. В репозитории лежит `.env.example`.
6. **Все допущения помечать** комментарием `# ASSUMPTION:` и перечислять в `docs/ASSUMPTIONS.md`. Реальные имена полей телеметрии, протокол и диапазоны команд пока неизвестны, поэтому они выдуманы и должны меняться только в конфиге и в одном файле адаптера.
7. **Не выдумывать лишнего.** Если что-то в ТЗ неоднозначно, выбрать простой вариант, записать решение в `docs/DECISIONS.md` и идти дальше. Не останавливаться на вопросах.

## 1. Контекст

Соревнование проходит 26–27 октября 2026. Команда из трёх человек (Оператор в Комплексе, Диагност и Инженер ИИ в Штабе) выполняет производственное задание (печатная плата и корпус) на автономном Комплексе «Купол» с ограниченными ресурсами. Во время зачётной игры (~90 минут) на Комплекс подаются кризисные воздействия: **прямые, скрытые, ложные и каскадные**. Оценивается производственный результат, устойчивость, диагностика, человеко-агентный контур и командное взаимодействие.

Комплекс состоит из четырёх систем:

| Система | Компоненты | Что доступно команде |
|---|---|---|
| Энергетическая | солнечные панели, инвертор, АКБ, распределительный щит | наблюдение за генерацией, зарядом, потреблением; включение и отключение разрешённых линий; смена разрешённых режимов |
| Телеметрия | датчики, контроллеры, видео, штатные каналы связи | просмотр текущих и исторических данных, сопоставление источников, связь Оператора и Штаба |
| Производственный контур | станок с ЧПУ, 3D-принтер, паяльная станция, измерительные приборы | только наблюдение статуса и передача указаний Оператору |
| Микроклимат | датчики температуры, влажности, CO2, вытяжка, увлажнитель | контроль параметров, управление разрешёнными режимами вытяжки и увлажнения |

### Жёсткие ограничения из регламента (код обязан их уважать)

- **Модель на зачётной игре только DeepSeek V4 Flash.** Любые другие модели и внешние сервисы запрещены (п. 10.6). Реализовать LLM-клиент так, чтобы модель и endpoint задавались конфигом, а любая другая модель в боевом режиме вызывала ошибку.
- **Аппаратные блокировки нельзя отключать, обходить или подавлять** (п. 9.2). Подача команд вне разрешённых диапазонов считается нарушением (п. 12.1).
- **Каждое значимое действие агента журналируется**; должно быть восстановимо, какие данные использовал агент, что вывел, что предложил или сделал и каков результат (п. 10.2–10.3).
- **У каждого агента есть заявленный резервный сценарий** на случай отказа, потери связи или низкой достоверности (п. 10.4).
- **Безопасность важнее производственного результата** (п. 1.5). При пайке обязательна вытяжка (п. 9.1).
- Прямого управления производственным оборудованием у Штаба нет, только указания Оператору.

## 2. Цель проекта

Построить каркас, на котором команда за три часа (13:45–16:45 подготовительного дня) соберёт боевую систему:

1. **Адаптер** к Комплексу с единым интерфейсом и **симулятор** Комплекса, чтобы разрабатывать и тренироваться без доступа к настоящему.
2. **Ядро**: состояние, журнал, детекторы аномалий, сверка источников, энергопланировщик, предохранитель команд.
3. **Агенты** на DeepSeek V4 Flash с детерминированным кодом вокруг и резервными сценариями.
4. **Панель Штаба** для людей с подтверждением действий агентов.

Главный принцип: **вся логика работает против абстрактного адаптера**. Утром должен меняться только `adapter/real.py` и `config.yaml`.

## 4. Функциональные требования по модулям

### 4.1. `core/models.py`

Описать типизированные модели (pydantic v2 или dataclass): `Telemetry` (снимок со временем), `Alert`, `Verdict`, `Command`, `CommandResult`, `JournalEntry`, `Recommendation`. Все с временем в UTC и в виде ISO-строки при сериализации.

Набор полей телеметрии (ASSUMPTION, имена условные):

- энергетика: `pv_power_w`, `battery_soc_pct`, `battery_voltage_v`, `load_total_w`, `lines` (словарь: имя линии, состояние вкл/выкл, потребление Вт);
- микроклимат: `temp_c`, `humidity_pct`, `co2_ppm` (несколько датчиков: `co2_ppm` как словарь `sensor_id -> value`), `vent_mode`, `humidifier_mode`;
- производство: `cnc_status`, `printer_status`, `solder_status` (`idle`, `running`, `error`, `unknown`);
- служебное: `comms_ok`, `data_age_s`.

### 4.2. `adapter/base.py`

Абстрактный класс `KupolAdapter` с методами:

- `get_telemetry() -> Telemetry`
- `get_history(field: str, minutes: int) -> list[tuple[datetime, float]]`
- `send_command(cmd: Command) -> CommandResult` (асинхронное принятие, результат проверяется отдельно)
- `is_connected() -> bool`

Все методы документированы, включая ожидаемые исключения (`AdapterTimeout`, `AdapterError`).

### 4.3. `adapter/simulator.py` (самый важный модуль)

Симулятор Комплекса с шагом времени (по умолчанию 1 секунда симуляционного времени, режим ускорения `--speed N`). Должен:

- моделировать энергобаланс: генерация панелей (зависит от «облачности»), потребление по линиям, заряд и разряд АКБ;
- моделировать микроклимат: CO2 растёт при работе людей, падает при вытяжке; влажность зависит от увлажнителя; температура растёт при пайке и работе станков;
- моделировать производственные устройства как конечные автоматы со временем выполнения и потреблением;
- принимать команды через `send_command`, применять с задержкой и **с возможностью отказа исполнителя** (команда принята, состояние не изменилось);
- загружать **сценарий** из `scenarios/*.yaml` и вбрасывать события в заданное время.

Типы событий в сценарии (обязательно реализовать все):

| Тип | Пример | Что делает симулятор |
|---|---|---|
| `direct` | падение генерации в 3 раза | реально меняет состояние системы |
| `hidden_drift` | медленный дрейф датчика температуры АКБ | дрейф показаний без реального изменения |
| `false_signal` | CO2 скачком до 5000 ppm на одном датчике | показание ложное, остальные датчики в норме |
| `cascade` | пайка требует вытяжку, она увеличивает нагрузку, АКБ разряжается | цепочка вторичных эффектов |
| `comms_loss` | пропажа телеметрии на N секунд | `comms_ok = False`, данные застывают |
| `actuator_fail` | вентиляция не реагирует на команды | команда принята, состояние не меняется |
| `device_fault` | остановка принтера или засор | статус устройства `error` |

Создать минимум **три готовых сценария**: `basic.yaml` (одно событие каждого типа), `cascade_heavy.yaml` (каскад на нехватке энергии), `quiet.yaml` (без событий, для проверки отсутствия ложных тревог). Симулятор обязан быть детерминированным при фиксированном `seed`.

### 4.4. `adapter/real.py`

Заглушка с правильной сигнатурой, `NotImplementedError` и подробным docstring с пошаговым описанием того, что нужно реализовать утром (протоколы REST, MQTT, WebSocket), и где менять маппинг имён полей. Пример-шаблон REST-клиента с таймаутами и повторами допустим.

### 4.5. `core/state.py`

Единая модель состояния Комплекса: последний снимок плюс кольцевой буфер истории (по умолчанию 15 минут, настраивается). Методы: `update(telemetry)`, `latest()`, `series(field, minutes)`, `slope(field, minutes)`, `age(field)`. Все агенты читают отсюда, а не напрямую из адаптера.

### 4.6. `core/journal.py`

Журнал решений в формате JSONL (машинный) плюс экспорт в CSV и в читаемую Markdown-таблицу для судей. Поля записи соответствуют п. 7.3 регламента:

`ts`, `actor` (человек или агент), `event`, `cross_check`, `hypothesis`, `impact`, `action`, `executor`, `result`, `status`.

Отдельный метод `log_llm_call(agent, prompt_hash, inputs_summary, raw_output, parsed_decision, used_fallback)` пишет каждый вызов модели (п. 10.2–10.3). Запись атомарная (flush после каждой строки), журнал не должен терять данные при падении процесса.

### 4.7. `core/guard.py`: предохранитель команд

Любая команда из любого агента или UI проходит только через `Guard.submit(cmd, requested_by)`. Он:

1. проверяет команду по **белому списку** и **допустимым диапазонам** из `config.yaml` (нарушение: отклонить, записать в журнал, не отправлять);
2. определяет класс команды: `auto` (агент может сам) или `needs_human` (требуется подтверждение человека). Класс задаётся в конфиге;
3. для `needs_human` ставит команду в очередь ожидания, а UI подтверждает или отклоняет;
4. после отправки **проверяет результат**: в течение `verify_timeout_s` состояние должно измениться ожидаемым образом, иначе создаётся тревога `actuator_no_effect`;
5. ограничивает частоту (не более N команд одному исполнителю за T секунд), чтобы агент не «заспамил» оборудование;
6. пишет всё в журнал.

Запрещено: любая команда, затрагивающая аппаратные блокировки. В коде это явный список запретов, проверка которого идёт раньше любых других.

### 4.8. `core/detectors.py` (без LLM, чистый код)

Детекторы, каждый возвращает `Alert` с уровнем (`info`, `warning`, `critical`):

- **Порог:** значение выше или ниже предела (warning и critical отдельно, из конфига).
- **Тренд:** наклон по скользящему окну превышает допустимый (ловит скрытый дрейф).
- **Скачок:** изменение за один такт больше допустимого (ловит ложные и прямые события).
- **Замерзание:** значение не менялось дольше N секунд при том, что должно меняться.
- **Устаревание:** данные не обновлялись дольше N секунд.

Каждый детектор настраивается через конфиг по каждому полю и покрыт тестами на синтетических данных.

### 4.9. `core/crosscheck.py`: сверка источников

Правила, возвращающие `Verdict(kind, confidence, explanation)`, где `kind` один из `real`, `false_signal`, `sensor_fault`, `unknown`:

- несколько датчиков одной величины: расхождение больше порога означает подозрение на сбой одного;
- CO2 высокий, а вентиляция, влажность и температура в норме, скачок резкий: вероятно ложный сигнал;
- **энергобаланс:** генерация минус потребление должна согласовываться с изменением заряда АКБ; расхождение означает, что врёт один из датчиков;
- статус устройства из телеметрии не совпадает с его потреблением (например, станок «running», а потребление нулевое).

Формула проверки баланса (для документации и тестов):

```latex
dE_{bat}/dt \approx P_{pv} - P_{load}, \qquad |dE_{bat}/dt - (P_{pv} - P_{load})| > \epsilon \Rightarrow \text{mismatch}
```

### 4.10. `core/energy.py`: энергобаланс и планировщик

- Расчёт суммарной нагрузки и **запаса времени до минимального заряда** `t_left`:

```latex
t_{left} = \frac{E_{bat} \cdot (SoC - SoC_{min})}{P_{load} - P_{pv}}, \quad P_{load} > P_{pv}
```

- Очередь операций из технологической карты (`config.yaml`: этапы, длительность, мощность, можно ли прерывать, нужна ли вытяжка). Приоритеты: безопасность (вытяжка при пайке), затем неприрываемые операции, затем остальное.
- Режим «что если»: `can_start(operation) -> (bool, reason)`, проверяет, хватит ли энергии, если начать операцию сейчас (с учётом вытяжки для пайки и текущей генерации).
- Рекомендация, что отложить или отключить при нехватке энергии, с объяснением.

### 4.11. `agents/llm.py`: обёртка модели

- Клиент DeepSeek V4 Flash (OpenAI-совместимый HTTP API; endpoint, имя модели и ключ из конфига и окружения).
- Таймаут, **один повтор**, затем **фолбэк**: вызывающий код получает флаг `used_fallback=True` и обязан применить правило в коде.
- Строгий JSON-вывод: схема в pydantic, валидация, при ошибке разбора один повтор с просьбой исправить формат, затем фолбэк.
- Режим `mock` (по умолчанию без ключа): детерминированные ответы-заглушки, чтобы весь проект работал и тестировался офлайн.
- В боевом режиме (`mode: competition`) запрещает любое имя модели, кроме разрешённого в конфиге. Попытка вызывает исключение.
- Каждый вызов пишется в журнал (см. 4.6). Хранится хэш промпта, а сами промпты лежат в `agents/prompts/` и версионируются git.

### 4.12. Агенты (`monitor.py`, `diagnost.py`, `energy_planner.py`)

Общий принцип: **код считает, LLM объясняет и ранжирует**. Решения, критичные для безопасности, никогда не отдаются на откуп модели.

| Агент | Вход | Выход | Автономность | Резервный сценарий |
|---|---|---|---|---|
| Монитор | снимок, алерты детекторов, вердикты сверки | краткая интерпретация для человека, приоритет | только рекомендации | показать сырые алерты без интерпретации |
| Диагност | алерты, вердикты, последние записи журнала | ранжированные гипотезы с вероятностями, **безопасная проверка** для каждой, рекомендуемое действие, нужен ли человек | только рекомендации | чек-лист п. 7.3 из кода |
| Энергопланировщик | баланс, очередь операций, мощности | порядок операций, что отложить | рекомендации, плюс разрешённая автономия для малорискованных режимов (например, увлажнитель) из конфига | расчёт по формуле из `core/energy.py` |

Требования: промпты в отдельных файлах, ответы строго по JSON-схеме, few-shot примеры из матрицы «симптом, причины, безопасная проверка» (она есть в `docs/`; если нет, создать пример из 8–10 строк), все вызовы идут через `llm.py`, все команды через `guard.py`.

### 4.13. `ui/dashboard.py`

Простая панель Штаба: консоль на `rich` или веб на Streamlit (выбрать один, записать в `DECISIONS.md`). Показывает:

- ключевые параметры (SoC, генерация, нагрузка, `t_left`, CO2, влажность, температура, статусы устройств);
- активные тревоги с уровнем;
- рекомендации агентов с кнопками «Принять» и «Отклонить»; подтверждение сразу пишется в журнал;
- ленту журнала (последние 20 записей);
- таймер игры и индикатор связи.

### 4.14. `main.py`

CLI с командами:

- `python -m kupol simulate --scenario scenarios/basic.yaml --speed 10 --seed 42` — прогон симулированной игры с агентами;
- `python -m kupol run --config config.yaml` — боевой режим с реальным адаптером;
- `python -m kupol replay logs/<run>/` — проигрывание сохранённой телеметрии и журнала после игры;
- `python -m kupol report logs/<run>/` — итоговый отчёт (Markdown): хронология, тревоги, решения, ложные срабатывания, использование LLM и фолбэков.

Главный цикл: опрос телеметрии, обновление состояния, детекторы, сверка, агенты, предохранитель, журнал. Устойчив к исключениям: сбой одного шага не должен останавливать цикл (логирует и продолжает). Корректно завершается по Ctrl+C с сохранением журнала.

## 5. Конфигурация (`config.yaml`)

Всё, что утром придётся менять, находится здесь и описано комментариями:

- пороги по каждому полю телеметрии (warning, critical, максимальный скачок, окно тренда);
- мощности оборудования и параметры энергосистемы (ёмкость АКБ, минимальный SoC, предел инвертора);
- белый список команд, допустимые диапазоны, класс (`auto` или `needs_human`), лимит частоты;
- технологическая карта изделия (этапы, длительность, мощность, прерываемость, вытяжка);
- таймауты: потеря связи, проверка результата команды, LLM;
- настройки LLM: `mode` (`mock`, `dev`, `competition`), модель, endpoint;
- пути журналов.

Валидация конфига при старте (pydantic): ошибка в конфиге должна быть понятной и приводить к остановке до начала игры, а не во время неё.

## 8. Критерии приёмки

Проект принят, если выполнены **все** пункты:

1. `pip install -e .` и `pytest` проходят без ошибок на чистой машине; `mypy` не падает на `core/` и `adapter/`.
2. `python -m kupol simulate --scenario scenarios/basic.yaml --seed 42` без ключа API (режим `mock`) доводит симулированную игру до конца и создаёт журнал.
3. В сценарии `basic` система: распознаёт **ложный сигнал** CO2 и не включает вытяжку на полную мощность; замечает **скрытый дрейф** по тренду раньше критического порога; фиксирует **отказ исполнителя** (команда без эффекта); корректно реагирует на **потерю связи**.
4. В сценарии `quiet` **нет** тревог уровня `critical` (нет ложных срабатываний).
5. Ни одна команда вне белого списка или диапазона не доходит до адаптера (есть тест).
6. Любая команда класса `needs_human` не выполняется без подтверждения (есть тест).
7. При недоступности LLM (имитировать таймаут) все три агента отдают результат по резервному сценарию, а в журнале стоит `used_fallback=true`.
8. В режиме `competition` попытка вызвать модель, отличную от DeepSeek V4 Flash, приводит к исключению (есть тест).
9. Каждый вызов LLM и каждая команда есть в журнале с достаточными данными для восстановления картины (п. 10.3 регламента).
10. `README.md` позволяет запустить проект за 5 минут; `docs/MORNING_CHECKLIST.md` пошагово описывает адаптацию под реальный Купол (что менять в `adapter/real.py`, `config.yaml`, промптах); `docs/ASSUMPTIONS.md` перечисляет все выдуманные допущения.
11. История git содержит осмысленные коммиты по плану из раздела 6, а не один общий.

## 9. Что не делать

- Не использовать никакие модели и внешние сервисы, кроме разрешённых в конфиге.
- Не добавлять код, обходящий белый список команд или предохранитель, даже «временно для отладки».
- Не отдавать моделям решения по безопасности, не перенося логику в код.
- Не хранить ключи, пароли и токены в репозитории.
- Не добавлять тяжёлые зависимости без необходимости (никаких фреймворков ради одного вызова).
- Не оставлять незадокументированный код и непокрытые тестами модули `core/`.
