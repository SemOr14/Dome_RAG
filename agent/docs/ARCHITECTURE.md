# Архитектура Штаба «Купол»

## Слои

```
            ┌──────────────────────────── ui/dashboard.py (Streamlit) ─────────────┐
            │  тревоги · вердикты · обход · пробы · прогноз · рекомендации · журнал │
            └───────────────▲───────────────────────────────────────┬──────────────┘
                   View (снимок для чтения)              очередь действий человека
┌─────────────┐   ┌─────────┴───────────────── engine.py ───────────┴──────────────┐
│ adapter/    │   │ такт (1 Гц): опрос → состояние → baseline → детекторы → сверка │
│  simulator  │──►│ → вердикты → реакция → пробы → обход → агенты → панель          │
│  real       │◄──│ команды: только через Guard                                      │
└─────────────┘   └──────────┬─────────────────────────┬────────────────────────────┘
   KupolAdapter              │                         │ ThreadPool (в mock — синхронно)
                  ┌──────────▼───────── core/ ─────┐  ┌▼──────────── agents/ ─────────┐
                  │ state · journal · guard         │  │ monitor · diagnost · energy_  │
                  │ baseline · detectors · crosscheck│  │ planner · llm (DeepSeek/mock) │
                  │ verdicts · response · probes    │  │ фолбэки по регламенту п. 10.4 │
                  │ round · energy · metrics        │  └────────────────────────────────┘
                  └─────────────────────────────────┘
```

Зависимости направлены вниз: `core/` ничего не знает об агентах и интерфейсе; агенты получают готовую «ситуацию»
(`agents/base.Situation`) и возвращают рекомендации; панель читает `Engine.view` и ставит действия человека в очередь.

## Адаптер (`adapter/`)

`KupolAdapter` — единственный интерфейс к Комплексу: `get_telemetry`, `get_history`, `send_command`, `now`,
`advance`. `SimulatorAdapter` живёт на виртуальном времени (`advance` двигает его, `--speed 0` без пауз), детерминирован
по seed и ведёт эталонную разметку воздействий (`ground_truth`) и журнал событий (`event_log`). `RealAdapter` — REST-шаблон
с таймаутами и повторами; три функции-переводчика надо дописать утром (см. `MORNING_CHECKLIST.md`).

Скрытые события симулятора (`hidden_load`, `sensor_drift_pair`, `silent_print_fail`, `frozen_sensor`, `noise_loss`,
`stale_timestamp`, `delayed_actuator`) не попадают в телеметрию в явном виде: проявляются только через косвенные
признаки. Составные события `false_then_real` и `cascade_trap` задают ловушки.

## Такт главного цикла (`engine.Engine.step`)

1. Опрос телеметрии; сбой опроса — запись в журнал, цикл живёт дальше. Любой шаг обёрнут в `_safe`: исключение шага
   журналируется и не останавливает игру.
2. События безопасности и действия человека из очередей (потокобезопасно).
3. `State` (кольцевой буфер, снимки с меткой времени не позже последней не принимаются), невязка энергобаланса.
4. `Baseline` — калибровка шума на начальном отрезке (5 минут) и медленное обновление вне тревог.
5. `DetectorSuite`: порог, тренд, скачок, замерзание, устаревание, физический предел скорости, монотонность времени,
   время до порога, разность пар, потеря шума, CUSUM (только разность пар и невязка баланса).
6. `CrossChecker`: правила сверки независимых источников (ложный CO2, энергобаланс, статус против потребления,
   причина–следствие после команды, тихий брак…). Каждое срабатывание — `Evidence` с весом из конфига.
7. `VerdictBook`: свидетельства накапливаются по предмету (`co2_ppm.co2_b`, `energy_balance`, пара `temp_c|temp_c_2`…),
   вид и уверенность вычисляет код.
8. `ResponsePolicy`: уровень реакции по вердикту и тревоге.
9. `ProbeManager`: безопасные пробы для спорных вердиктов; `RoundChecklist`: «Обход» по таймеру.
10. Агенты (по расписанию и по тревогам), сбор результатов, публикация `View` для панели.
11. `adapter.advance`.

## Вердикты и свидетельства

`Verdict(kind, status, evidence[])`. Вероятность «реальный» —
`p = σ(bias + scale · Σ ±w · 0.5^(возраст/half_life))`; пороги `real_above` / `false_below`, потолок уверенности
`max_confidence`. Веса, масштаб и период полураспада — в `config.yaml → verdicts`. Уверенность считает код;
модель лишь называет гипотезы (вероятности гипотез Диагноста тоже пересчитываются кодом).

Жизненный цикл: `provisional` → автоматическая перепроверка через `recheck_after_s` (60 с) → `confirmed`.
Вердикт «ложный» **не закрывается навсегда**: ещё `watch_after_false_s` (300 с) он под наблюдением, новые
свидетельства «за реальный» переводят его в `unknown` / `real` (событие `reclassified` / `revised`) и поднимают тревогу
пересмотра. Человек может закрыть вердикт вручную (`close_manual`). Свидетельства постепенно теряют вес, чтобы
вердикт мог «забыть» старое.

## Уровни реакции (`core/response.py`)

`observe` → `prepare` → `act_reversible` → `act_full`. Порог по уверенности для каждого уровня — в
`response.*`. Ограничения:

- **Правило двух**: действие `act_full` и команда с `costly: true` требуют не менее двух независимых источников
  свидетельств (`min_sources_full`). Исключение — события безопасности (`smoke`, `solder_overheat`, `operator_stop`):
  правило двух не применяется, но белый список и диапазоны команд действуют.
- Прогноз времени до порога сам по себе поднимает реакцию не выше `prepare`.
- Максимальный уровень по тревоге ограничен `response.max_level_by_alert`.
- Команда, не набравшая оснований, понижается (`CommandStatus.DOWNGRADED`) и пишется в журнал.

## Guard (`core/guard.py`) — единственный путь команд

Порядок проверок: запреты по подстрокам (`interlock`, `bypass`, `override`…; регламент п. 9.2, 12.1) → белый список и
диапазоны аргументов → rate-limit → правило двух и защита от каскада (после дорогого действия запас энергии не
должен падать ниже `cascade_min_t_left_min`) → класс `auto` / `needs_human` (очередь подтверждения с TTL) →
отправка адаптеру → проверка эффекта (`verify`, тревога `actuator_no_effect`) с учётом запоздалого эффекта
(`late_effect_window_s`) → запись в журнал на каждом шаге. Пробы, ответы агентов, действия человека и симулятора —
все команды идут через этот же Guard.

## Baseline (`core/baseline.py`)

Калибруются **только** величины, не зависящие от режима оборудования: шум датчика после вычитания линейного
тренда (поддоконные σ, медиана), разность пар датчиков (медиана), σ невязки энергобаланса. Абсолютные уровни,
пороги и z-score по режимам не калибруются и не хранятся; данные периода тревоги в baseline не попадают. Снимок
(`BaselineSnapshot`) проверяется по полям при загрузке.

## Пробы (`core/probes.py`) и «Обход» (`core/round.py`)

Каталог проб — в `config.yaml → probes.catalog` (стоимость, риск, оценка информативности, ожидаемый результат при
«реальный»/«ложный»). Выбор пробы — по информативности в пределах бюджета (`max_per_10min`, `energy_budget_wh`,
`min_gap_s`). Проба с командой (`vent_min_30s`) идёт через Guard; вопросы Оператору (`operator_check_indicator`,
`video_check`) отображаются в панели. Результат пробы — новое свидетельство вердикта.

«Обход» раз в `round.interval_s` (420 с) открывает чек-лист пар источников; отметка «расхождение» создаёт тревогу.

## Агенты (`agents/`)

`monitor` — подготовка рекомендаций по тревогам и реакции по CO2; `diagnost` — гипотезы, безопасные проверки и
пробы (≥ 8 примеров в `prompts/examples/`, фактически 12); `energy_planner` — `t_left`, очередь операций,
что отложить. `llm.LLMClient`: `mock` / `dev` / `competition`, строгий JSON, один ретрай разбора, таймаут, любой сбой —
резервный сценарий (`used_fallback=true`), каждый вызов — запись `llm_call` в журнале. В `competition` любая модель,
кроме `deepseek-v4-flash`, вызывает `ForbiddenModelError`. Придуманные моделью пробы (которых нет в каталоге)
отбрасываются.

## Графики панели (`core/charts.py`, `ui/charts.py`)

Вкладка «Графики» показывает то, на чём держатся решения. `ChartRecorder` в конце каждого такта копит числа, которые
движок уже посчитал (новых вычислений для решений нет): телеметрию, запас `t_left`, невязку баланса, накопление CUSUM,
разности пар в σ (с учётом смещения из baseline), вероятность «реальный» по вердиктам (`VerdictBook.probabilities`) и
наибольший уровень реакции. Пишет поток движка, читает поток панели (под блокировкой); на ряд хранится до 8000 точек,
при чтении ряд прореживается до 600.

Три раздела: «Энергия» (мощность, заряд, запас времени, напряжение и температура АКБ), «Микроклимат» (CO2 по датчикам,
два датчика температуры, влажность) и «Диагностика решений» (невязка баланса с ±3σ, CUSUM с порогом, пары датчиков
с коридором, вероятности вердиктов с границами «реальный»/«ложный», уровень реакции). Линии порогов берутся из тех же
разделов конфигурации, что у детекторов (`thresholds`, `energy`, `detectors`, `verdicts`), поэтому линия на графике и
тревога согласованы. Далёкий порог не сплющивает график: числа порогов всегда в подзаголовке, линия появляется, когда
значение к ней приблизилось. Окно — 5 мин, 15 мин или вся игра. Вкладка живёт в собственном фрагменте Streamlit и обновляется раз в 10 с (кнопка «Обновить» — сразу): каждое обновление перерисовывает график целиком, и при секундном обновлении он мигает. Шапка и вкладка «Штаб» обновляются раз в секунду отдельными фрагментами.

## Журнал и артефакты прогона

`logs/<время>-<сценарий>/`: `journal.jsonl` (+ `.csv`, `.md`), `telemetry.jsonl`, `meta.json`, `summary.json`,
для симулятора ещё `sim_events.jsonl` и `ground_truth.jsonl`. Записи журнала соответствуют полям п. 7.3 регламента
(`ts, actor, event, cross_check, hypothesis, impact, action, executor, result, status`) плюс машинные подробности в
`data`. Виды: `decision`, `llm_call`, `alert`, `verdict`, `command`, `recommendation`, `agent`, `response`, `probe`,
`round`, `baseline`, `error`, `engine`, `human`. Журнал пишется построчно с flush — обрыв процесса не портит записанное.

## Потоки

Основной цикл — один поток. Агенты в `ThreadPoolExecutor` (в режиме `mock` — синхронно, для детерминизма);
медленная модель не задерживает опрос, по таймауту включается фолбэк. Панель: движок живёт в фоновом потоке
(`st.cache_resource`), страница обновляется фрагментом `run_every=1`; кнопки кладут действия в потокобезопасную очередь,
которую движок разбирает в начале такта.

## Метрики (`core/metrics.py`)

По журналу и эталонной разметке: обнаружение и задержка по каждому воздействию, упреждение относительно критического
порога, верность вердиктов, ложные срабатывания на час вне окон воздействий, своевременность пересмотров, каскады
(вредные команды в окнах ловушек), использование LLM / проб / реакций. Раздел «Метрики качества» входит в `report`,
сводка по сценариям и seed — в `benchmark` (`docs/BENCHMARK.md`).

## Соревновательный рантайм (`src/kupol/dome/`)

```
 client.py ──► state.py ──► playbooks/* ──► runner.py ──► gate.py ──► client.control ──► купол
 (WebSocket)   (узлы,      (намерения:      (решение →    (политика,    (только при DOME_ALLOW_CONTROL=1,
               история)     что видим,       лог →         защитные      иначе dry_run в логе)
                            почему, шаги)    шаги →        правила)
                                             сообщение)       │
                                    rag.py / llm.py ◄─ советы │      verification по телеметрии
```

- `client.py` — авторизация, запросы по `request_id`, переподключение (пауза растёт 3 → 30 с), роль `guest`,
  `session_revoked`, лимит 4 запроса/с.
- `state.py` — последние значения узлов, ряды чисел, «замёрзшие» узлы (по `status`/`updated_at`).
- `checks.py` — сверки: CO₂ по трём датчикам (скачок, расхождение с согласными), конденсат, дым, принтер
  (`webhook_state`), энергия; уверенность — сигмоида суммы весов свидетельств.
- `playbooks/` — `air` (CO₂, конденсат), `machines` (продолжение станков, дым), `production` (принтер и бокс),
  `energy` (режим инвертора, E09, MPPT, IL_LOAD_SHED), `lines` (фантомная линия, IL_OVERCURRENT, защита),
  `devices` (аварии, замёрзшие узлы, время, связь), `tasks` (чат Оператора). Плейбук возвращает `Intent`
  (ситуация, причина, уверенность, свидетельства, план, шаги, сообщение) и не отправляет ничего сам.
- `gate.py` — единственный путь команд: роль → каталог → политика `dome.yaml` → значение → защитные правила
  (resume, start_job, замок бокса, дребезг линий, доверие датчикам, возраст телеметрии) → отправка → `verification`.
- `runner.py` — такт: телеметрия → плейбуки → решения по приоритету (кулдауны) → шаги через Gate → сообщение
  Оператору только если все шаги приняты → наблюдение раз в 45 с → сохранение состояния.
- `agentlog.py` — лог по §5 требований; `tools/check_agent_log.py` проверяет формат и цепочки `ref`.
- Тесты: `tests/dome_fake/` (WebSocket-эмулятор + модель купола с правилами сервера), `tests/fixtures/` (снимки из
  журнала 14.10), сценарные тесты `tests/test_dome_scenarios.py`.
