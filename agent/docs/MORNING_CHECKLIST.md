# Утренний чек-лист: адаптация под реальный Купол

Всё, что выдумано для симулятора, лежит в `config.yaml` и в `src/kupol/adapter/real.py`. Остальной код менять не
нужно. Порядок: сначала подключение (части A–C), затем подгонка детекторов (часть D, около 10 минут), затем
репетиция (часть E). Каждый шаг можно проверить командой из последнего столбца.

## A. Окружение (5 минут)

| № | Шаг | Проверка |
|---|---|---|
| A1 | `python -m venv .venv` и `.venv\Scripts\python -m pip install -e ".[dev]"` | `.venv\Scripts\python -m pytest -q` — зелёный |
| A2 | Скопировать `.env.example` в `.env`, вписать `DEEPSEEK_API_KEY` (и `KUPOL_API_TOKEN`, если нужен) | `.env` не попадает в git (`git status`) |
| A3 | Сверить с документацией API: `llm.base_url` и `llm.model` в `config.yaml` (допущение: `https://api.deepseek.com`, `deepseek-v4-flash`) | `python -m kupol simulate --scenario scenarios/basic.yaml --llm-mode dev --duration 300` — в журнале записи `llm_call` без ошибок |
| A4 | Для игры: `llm.mode: competition` (запрещает любую другую модель, регламент п. 10.6) | `ForbiddenModelError` при чужом имени модели |

Реальные вызовы DeepSeek в ходе разработки не выполнялись: имя модели, endpoint и формат ответа не проверены.

## B. Реальный адаптер (`adapter/real.py`)

1. Узнать у организаторов протокол (REST / MQTT / WebSocket). Для REST поправить раздел `real` в `config.yaml`
   (`base_url`, `telemetry_path`, `history_path`, `command_path`, `token_env`). Для MQTT/WebSocket заменить `_request`.
2. `map_telemetry`: сопоставить реальные поля с `Telemetry` (время в UTC; Вт, %, В, °C, ppm). Это единственное место,
   где имена полей Комплекса встречаются с нашими. Если у Комплекса нет второго датчика температуры, `temp_c_2`
   оставить пустым (пара `temp_c|temp_c_2` в `detectors.pair_diff.groups` тогда убрать).
3. `map_history`: ответ истории → список `(время UTC, значение)`; запрос строится по плоскому имени поля
   (`co2_ppm.<датчик>`, `lines.<линия>.power_w`).
4. `encode_command` / `decode_command_result`: наша `Command` ↔ тело запроса и ответ API.
5. Проверка: `python -m kupol run --config config.yaml` делает пробный запрос телеметрии при старте и останавливается
   с понятным сообщением, если `map_telemetry` ещё не написан.

## C. Команды и линии (`config.yaml → guard`, `equipment`)

1. Привести имена команд, аргументов и допустимые диапазоны в `guard.commands` к реальному API. В Комплекс уйдёт только
   то, что перечислено; всё остальное и все запрещённые подстроки (`guard.forbidden`) отклоняются до адаптера.
2. Проверить классы: `auto` — агент может сам, `needs_human` — только после подтверждения человека, `costly: true` —
   дорогое действие (правило двух). Не ослаблять без причины.
3. `equipment.lines` — реальные линии щита и номинальные мощности; `equipment.device_lines` — какой статус устройства
   соответствует какой линии. `energy.battery_capacity_wh`, `soc_min_pct`, `inverter_limit_w` — по паспорту Комплекса.
4. Режимы в YAML с `"off"` писать в кавычках (иначе YAML прочитает `false`).

## D. Подгонка детекторов под реальный Купол (≈ 10 минут)

Принцип: ни один шаг ниже не требует задавать ожидания «в режиме X должно быть Y». Подгоняются только физические
пределы датчиков и пары; всё, что зависит от режима оборудования, оценивается по данным текущей игры.

Подготовка: запустить `python -m kupol run` (или записать 5–10 минут телеметрии при спокойной обстановке), затем
изучить `logs/<прогон>/telemetry.jsonl` и записи `kind=baseline` в `journal.jsonl`. Для интервала спокойной работы
(без событий) снять значения по каждому полю и подставить так:

| Параметр | Как подогнать | Как проверить |
|---|---|---|
| `detectors.max_rate_per_s` | Найти наибольший шаг между соседними снимками за спокойный интервал (единиц/с) и взять 2–3-кратный запас. Физический предел: быстрее среда меняться не может. Для CO2 учесть дыхание рядом с датчиком | В спокойный интервал нет тревог `rate_limit` |
| `detectors.pair_diff.max_abs_diff` | Взять максимальную разность между датчиками одной пары за спокойный интервал и умножить на 1,5–2. Этот предел действует всегда, в том числе пока baseline не набран | Нет тревог `pair_diff` на спокойном интервале; при искусственном расхождении (приложить датчик к источнику) тревога срабатывает |
| `detectors.pair_diff.groups` | Перечислить реальные группы одноимённых датчиков (плоские имена полей). Пара в группе — это то, что должно быть равно по смыслу | В «Обходе» (`round.pairs`) те же пары |
| `detectors.pair_diff.max_diff_slope_per_min`, `corridor_k`, `confirm_ticks` | Ослабить, если разность пар «дышит» быстрее; `confirm_ticks` увеличить при шумном канале | Тревог `pair_diff` на спокойном интервале нет |
| `detectors.freeze_s` | Реальные датчики могут быть квантованы: найти самый долгий интервал без изменения значения при живом процессе и взять вдвое больше. Для медленных величин (температура, влажность) значения больше | Нет тревог `freeze` на спокойном интервале; на отключённом датчике тревога через `freeze_s` |
| `detectors.noise_loss.min_noise_ratio` | Оставить 0,1; если реальный шум датчика сильно меняется между режимами, снизить | Нет тревог `noise_loss` на спокойном интервале |
| `thresholds.*` (`warn_*`, `crit_*`, `max_jump`, `max_slope_per_min`) | Привести к значениям из регламента и паспорта Комплекса | Нет тревог на спокойном интервале |
| `crosscheck.balance_eps_w`, `energy.charge_efficiency`, `discharge_efficiency`, `balance_bias_w` | Реальный SoC шумнее и не гладкий: поднять `balance_eps_w`, пока невязка баланса на спокойном интервале не перестанет давать `energy_balance` | В `journal.jsonl` нет свидетельств `energy_balance` на спокойном интервале |
| `process.operations` | Технологическая карта изделия: длительности, мощности этапов, `needs_vent`, `depends_on`, `device_line` по реальному плану команды | `Энергопланировщик` показывает реальные этапы и `t_left` |
| `probes.max_per_10min`, `energy_budget_wh`, `min_gap_s`, `probes.catalog` | Бюджет проб за 10 минут: по умолчанию 3 пробы и 5 Вт·ч. Увеличить, если энергии с запасом; уменьшить, если вытяжка в проб-режиме мешает. Пробы с командами используют имена из `guard.commands` | В панели «Безопасные пробы» не больше `max_per_10min` за 10 минут |
| `round.interval_s`, `round.pairs` | Периодичность и пары для сверки глазами по реальным приборам | В панели блок «Обход» показывает нужные пары |
| `verdicts.weights`, `aggregation.scale` | Не трогать, пока нет данных реальной игры. Вес правила — доверие к источнику | — |

### Проверка окна калибровки (5 минут)

Окно калибровки — `baseline.window_s` = 300 с с начала игры (регламент п. 6.5 фиксирует исходное состояние):

1. Дождаться записи в журнале `калибровка набрана` (`kind=baseline`, ровно через `window_s` после старта).
2. В `data.baseline.noise` — σ шума каждого поля: значения должны быть положительными и близкими к тому, что видно по
   спокойным данным (например, шум CO2 в единицах ppm, температуры — в сотых долях °C). `subwindows` должно быть не
   меньше `baseline.min_subwindows` (по умолчанию 3; при `window_s=300` и `subwindow_s=30` — 10).
3. В `data.baseline.pair_offset` — смещение каждой пары (разность медианой): небольшое, сравнимое с известной
   погрешностью датчиков. Если смещение огромно, пара неправильная или датчики не идентичны: поправить `groups`.
4. `balance_sigma` — σ невязки энергобаланса; не опускается ниже `baseline.balance_sigma_floor_w`. Если реальная
   невязка шумит заметно сильнее, поднять пол.
5. Если в окне калибровки идут события (запуск станков, смена режима вытяжки), это не помеха для шума после вычитания
   тренда; тревоги уровня warning и выше блокируют калибровку своих полей. Если калибровка не набралась (ни одной записи
   `baseline`), увеличить `baseline.window_s` или проверить, не блокирует ли её постоянная тревога.
6. Абсолютные уровни в baseline не хранятся — проверять их не нужно: `BaselineSnapshot` содержит только σ, смещения пар
   и σ невязки.

## E. Репетиция

1. `python -m kupol dashboard --scenario scenarios/mixed.yaml` на ноутбуке: проверить, что панель открывается,
   кнопки подтверждения, «Выполнить пробу», «Закрыть вручную» и события безопасности работают, блок «Обход» по
   таймеру (420 с) открывается.
2. `python -m kupol benchmark --scenarios scenarios/ --seeds 1-5` — убедиться, что после правок конфига метрики не
   испортились (на `quiet` — ноль critical, ≤ 1 warning в час; на `traps` — ноль каскадов).
3. Запуск на реальном Комплексе: `python -m kupol dashboard` (без `--scenario`) или `python -m kupol run`.
   Журнал прогона — `logs/<время>-*/`; он нужен для отчёта организаторам (регламент п. 7.3): `python -m kupol report
   logs/<прогон>`.
4. Перед стартом: `git status` чистый, `pytest` зелёный, `llm.mode: competition`.

## Что не нужно делать утром

- Не задавать ожидаемые значения по режимам оборудования («в режиме пайки CO2 должен быть ...»): детекторы и baseline
  на них не опираются.
- Не отключать `guard.forbidden` и не расширять белый список команд без согласования с регламентом п. 9.2 и 12.1.
- Не хранить ключи в `config.yaml` и в git.
